# AGENTS.md

Общий рабочий регламент пользователя, Codex и ChatGPT в проекте Vico Forum.

## Роли

1. Пользователь — владелец проекта: принимает продуктовые и спорные решения и выполняет merge.

2. Codex — технический руководитель, архитектор и независимый reviewer: свободно анализирует архитектуру, предлагает и оспаривает технические решения, определяет технический план и проверяет реализацию. Саму реализацию проекта не выполняет.

3. ChatGPT — архитектор, независимый reviewer и исполнитель ограниченных изменений.

## Диагностика перед выбором решения

1. До предложения технического изменения, обходного решения или действия пользователю ChatGPT самостоятельно проверяет фактические симптомы, ожидаемое поведение и все существенные звенья причинно-следственной цепочки до наблюдаемого результата. Первая найденная ошибка или ограничение не завершает диагностику.

2. Проверять альтернативные причины и последующие ограничения, способные изменить вывод или выбранное решение; если известен ранее работавший штатный путь, сопоставить его с текущим. Отделять подтверждённые факты от гипотез и не выдавать правдоподобное объяснение за установленную причину.

3. Переходить к исправлению, когда имеющихся проверяемых данных достаточно, чтобы обосновать причинную связь и выбранное решение, а оставшиеся неопределённости не меняют его. Не требовать проверки несвязанных частей системы.

4. До привлечения пользователя выполнить все доступные и разрешённые ChatGPT проверки и диагностические действия. Запрашивать участие пользователя только при установленной необходимости его полномочий, выбора или недоступного ChatGPT действия; не перекладывать на него доступную самостоятельную диагностику.

5. До выбора обходного решения проверить возможность восстановления штатного пути и устранения причины. Обход обозначать как обход, а не как исправление первопричины.

6. Если существенные обстоятельства нельзя проверить, явно указать «Информация не проверена» и границы установленного. Не предлагать изменение на неподтверждённом основании; допустимый диагностический эксперимент не представлять окончательным исправлением. Правила разрешений для действий с внешними последствиями сохраняются.

## Рабочий процесс

1. GitHub `main` — источник истины для текущего проекта.

2. В проекте используется один общий служебный PR ChatGPT + Codex. Он служит постоянным техническим каналом между ними и никогда не merge в `main`.

3. В общем служебном PR существует один communication-файл. ChatGPT и Codex читают и обновляют его напрямую. В нём ведутся передача работы, текущий статус, технические аргументы, согласование findings, подтверждённые рабочие решения, незакрытые вопросы и следующий шаг.

4. Общий служебный PR используется для технической работы ChatGPT и Codex: передачи задач и результатов, обсуждения и проверки решений, согласования findings, фиксации текущего состояния и следующих шагов. Основной рабочий материал — общий communication-файл.

5. Для каждой реализации используется отдельный implementation PR. В нём находятся только изменения проекта, CI/checks и результаты вручную запущенного Codex review.

6. Implementation PR не используется как основной канал общения ChatGPT и Codex. Findings из Codex review и результаты независимой проверки переносятся в общий служебный PR для сравнения, обсуждения и технического согласования.

7. Реализацию выполняет ChatGPT. Codex не изменяет implementation-код, проектную документацию, конфигурацию, миграции или implementation-ветку; он может изменять общий communication-файл и оставлять review findings в implementation PR.

8. Пользователь не передаёт сообщения между ChatGPT и Codex. Он подключается только когда требуется его продуктовое решение, выбор между технически допустимыми вариантами или действие, доступное только владельцу.

9. Codex Code Review implementation PR запускается вручную только для head, который ChatGPT считает финальным и готовым к merge. Промежуточные commits и heads на Codex review не отправляются.

10. До ручного Codex review ChatGPT завершает реализацию, собственную проверку, относящиеся к задаче CI/checks, Pages/browser review и owner visual acceptance, если они применимы, а также необходимые изменения project state/documentation. После этого implementation head не должен планово меняться.

11. Merge всегда выполняет только пользователь.

## Действие пользователя

1. Каждый ответ ChatGPT и Codex начинается с заголовка `Действие пользователя`; под ним указывается только следующее действие пользователя.

2. Если действие пользователя не требуется, указывается `Ничего.`

3. Ручная передача сообщения другому участнику используется только как аварийный fallback, если общий служебный канал технически недоступен.

## Общие правила

1. У пользователя нет локальной копии проекта.

2. Перед изменением проекта полностью прочитать актуальные `PROJECT.md`, `PROJECT_STATE.md` и относящиеся к задаче source-of-truth документы до фактического конца.

3. Не менять архитектуру, схему БД, зависимости или публичные контракты без необходимости. Не выполнять несвязанный рефакторинг и работу будущих Stage без текущей необходимости.

4. Изменения должны быть ограниченными и удобными для проверки.

5. Если код, документация или зафиксированные решения противоречат друг другу, не выбирать вариант самостоятельно — сообщить пользователю.

6. Перед использованием внешнего API, библиотеки или инструмента проверить актуальную официальную документацию. Не заявлять о проверках, которые фактически не выполнялись.

7. Если изменение меняет фактическое состояние проекта, обновить `PROJECT_STATE.md` в том же наборе изменений. Не фиксировать заранее результаты незавершённых CI, acceptance или external verification.

8. Production deployment, production-данные, секреты, платные ресурсы и другие труднообратимые внешние действия выполнять только после явного разрешения пользователя.

9. Текущий Stage, его границы и обязательные проверки определяются `PROJECT_STATE.md`, `ROADMAP.md` и профильной документацией.

## Независимая проверка PR

1. ChatGPT сначала самостоятельно проверяет весь implementation PR против исходной задачи, актуального проекта и относящейся документации и устраняет подтверждённые им дефекты до вызова Codex.

2. Когда implementation head стабилен и считается готовым к merge, ChatGPT один раз запускает ручной Codex review этого exact head. До завершения независимого Codex review ChatGPT не передаёт Codex собственные выводы по PR, если это технически возможно.

3. Каждый возможный finding сначала классифицируется как:
   - реальный дефект текущего Stage;
   - только задел на будущее.

   Задел на будущее сам по себе не является основанием для исправления.

4. После независимого Codex review его findings и результат whole-PR проверки ChatGPT переносятся в общий служебный PR и сравниваются там.

5. Если ChatGPT и Codex независимо обнаружили одну проблему и выводы совпадают, finding считается подтверждённым.

6. Если выводы расходятся, аргументы обсуждаются в общем служебном PR до технического консенсуса. Ни позиция ChatGPT, ни позиция Codex заранее не считается правильной.

7. Если вопрос является выбором между несколькими технически допустимыми вариантами, решение принимает пользователь.

8. Исправляются только подтверждённые findings текущего Stage. Если подтверждённых findings несколько, ChatGPT по возможности исправляет их одним согласованным пакетом, а не запускает новый review после каждого отдельного исправления.

9. Повторный Codex review запускается только если после предыдущего Codex review из-за подтверждённых findings реально изменилась реализация: логика, данные или запросы, permissions, routes/actions, компоненты, стили, тесты либо другая implementation-часть PR.

10. Перед повторным Codex review ChatGPT снова выполняет собственный whole-PR review и относящиеся проверки; затем один раз отправляет новый стабильный exact head Codex.

11. Если после Codex review изменены только документация, запись owner acceptance или communication-файл и сама реализация не изменилась, новый Codex review не запускается.

12. Цикл завершается, когда финальный Codex review и whole-PR review ChatGPT не оставляют подтверждённых дефектов текущего Stage.

## Полный аудит документации

1. Этот режим используется только по прямому запросу пользователя.

2. Каждый документ из заданного объёма читается полностью до фактического конца.

3. Аудит нельзя называть полным, если часть заявленного объёма не проверена.

4. Подтверждённые несоответствия отделяются от предположений и вопросов, которые невозможно установить по проверенным материалам.
