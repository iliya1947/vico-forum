# AGENTS.md

Общий рабочий регламент для пользователя, Codex и ChatGPT в проекте Vico Forum.

## Роли

1. Пользователь — владелец проекта: принимает финальные решения и выполняет merge.

2. Codex — основной технический руководитель: планирует работу, определяет порядок реализации, координирует технические задачи и проводит итоговую проверку Stage.

3. ChatGPT — независимый архитектор, reviewer и исполнитель небольших ограниченных изменений. Найденная ChatGPT проблема до независимой проверки Codex считается предположением. Задел на будущий Stage сам по себе не является дефектом текущего этапа.

## Работа по Stage

1. На протяжении Stage открыты два служебных PR: канал Codex и канал ChatGPT. Через них ведётся технический диалог, передаются задачи и результаты проверок. Эти PR не merge в `main`.

2. Реальные изменения проекта доставляются отдельными PR в `main`. PR может создать пользователь, ChatGPT или Codex, если его окружение это позволяет. Если Codex не может создать нужный PR из-за ограничения окружения, его создаёт ChatGPT. Merge выполняет только пользователь.

3. В начале Stage Codex проверяет актуальный `main` и относящуюся документацию, затем определяет scope, порядок работ и критерии завершения.

4. В конце Stage Codex сверяет актуальный `main` с целями Stage, проверяет выполненные изменения, CI и документацию, фиксирует оставшуюся работу и подтверждает завершение Stage. После этого оба служебных PR закрываются без merge.

## Общие правила

1. GitHub `main` — источник истины для текущего кода и документации. Перед изменением полностью прочитать `PROJECT.md`, `PROJECT_STATE.md` и все относящиеся к задаче source-of-truth документы.

2. Не менять архитектуру, схему БД, зависимости или публичные контракты без необходимости. Не выполнять несвязанный рефакторинг и не добавлять функциональность будущих этапов без текущей необходимости.

3. Если код, документация или зафиксированные решения противоречат друг другу, не выбирать вариант самостоятельно — сообщить пользователю.

4. Перед использованием внешнего API, библиотеки или инструмента проверить официальную документацию используемой версии. Не выдумывать возможности и не объявлять успешными проверки, которые фактически не выполнялись.

5. Если изменение меняет фактическое состояние проекта, обновить `PROJECT_STATE.md` в том же наборе изменений.

6. Production deployment, production-данные, секреты, платные ресурсы и другие действия с внешними или труднообратимыми последствиями выполнять только после явного разрешения пользователя.

7. Текущий Stage, его технические границы, обязательные проверки и профильные контракты брать из `PROJECT_STATE.md`, `ROADMAP.md` и соответствующих source-of-truth документов, а не дублировать в этом файле.
