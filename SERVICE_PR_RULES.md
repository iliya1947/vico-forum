# Правила работы со служебным PR

Этот файл задаёт структуру и правила использования служебных PR проекта Vico Forum.

При создании нового служебного PR актуальный `SERVICE_PR_RULES.md` из `main` копируется в корень его ветки как `RULES.md`.

Для существующего служебного PR действует его локальный `RULES.md`. `AGENTS.md` имеет приоритет.

## 1. Назначение

Служебный PR — рабочая память и координационный канал команды по одной задаче.

По нему агент должен без пересказа разработчика понимать:

1. цель и границы задачи;
2. текущее состояние и своё назначение;
3. принятые решения и существенный общий контекст;
4. технический контекст своей работы;
5. следующий рабочий переход.

Служебный PR не является implementation PR, продуктовой документацией или архивом переписки.

## 2. Базовая структура

В корне:

```text
RULES.md
TASK.md
WORKFLOW.md
COMMUNICATION.md
DECISIONS.md
HISTORY.md
AGENT_ERRORS.md
```

Личная память:

```text
agents/
  mira.md
  lira.md
  mark.md
  leva.md
```

Отдельные этапы при необходимости:

```text
stages/
  <stage>/
```

Дополнительные рабочие области:

```text
research/
scratch/
```

Количество файлов не ограничивается. Структура должна помогать разделять контекст, а не создавать пустые файлы ради шаблона.

## 3. Общие файлы

1. `TASK.md` — цель всей задачи, её границы, крупная структура и критерий завершения.

2. `WORKFLOW.md` — единственный источник текущего оперативного состояния: активный этап, назначение, исполнитель, PR/head, проверка, блокер и следующий переход. Старые состояния здесь не накапливаются.

3. `COMMUNICATION.md` — общий актуальный контекст команды: существенные факты, ограничения, зависимости, договорённости, незакрытые вопросы и блокеры, которые должны знать несколько агентов.

4. `DECISIONS.md` — действующие принятые решения. Для удобства можно использовать идентификаторы `D-01`, `D-02` и т. д. Обсуждение вариантов здесь не хранится.

5. `HISTORY.md` — значимые завершённые события задачи: этапы, merge, существенные изменения плана, переназначения, закрытые важные findings, эскалации и переходы. Это не источник текущего состояния.

6. `AGENT_ERRORS.md` — подтверждённые ошибки агентов, из которых есть полезный урок. Запись должна кратко фиксировать, что произошло, почему это было ошибкой и как предотвращать повторение. Мелкие промахи сюда не заносятся.

## 4. Личные файлы

`agents/<agent>.md` — персональная рабочая память агента.

Там хранится только то, что полезно именно этому агенту при продолжении работы:

1. собственные существенные выводы;
2. важный технический контекст;
3. незавершённые линии анализа;
4. персональные следствия общих решений;
5. ссылки на нужные рабочие материалы.

Личный файл не должен превращаться в хронологический дневник, копию `WORKFLOW.md` или склад чужих результатов.

Агент поддерживает свой файл в актуальном состоянии. Чужие личные файлы читаются только при конкретной необходимости.

## 5. Этапы

Для самостоятельного рабочего этапа можно создать:

```text
stages/<stage>/
  SCOPE.md
  PLAN.md
  REVIEW.md
  RESULT.md
```

Используются только нужные файлы.

1. `SCOPE.md` — границы и результат этапа, если их полезно отделить от плана.

2. `PLAN.md` — актуальный технический план этапа.

3. `REVIEW.md` — состояние проверки реализации: PR/head, подтверждённые findings и итоговый результат проверки.

4. `RESULT.md` — компактный итог завершённого этапа, если он нужен последующим этапам.

Для маленького этапа scope может быть частью `PLAN.md`. Для сложного этапа план можно разбить на несколько смысловых файлов.

Структура этапа определяется его реальной сложностью.

## 6. Research и scratch

1. `research/` — самостоятельные технические исследования, альтернативы, эксперименты и доказательства. Принятый результат исследования должен быть отражён или связан с соответствующим планом или решением.

2. `scratch/` — временные материалы агента. Другие агенты не обязаны их читать. Перед передачей работы всё существенное переносится в постоянный рабочий контекст.

## 7. Актуальность и дублирование

Рабочие файлы отражают актуальное состояние, а не последовательность всех прежних состояний.

Git уже хранит историю изменений.

Не следует копировать большие блоки одной и той же информации в несколько файлов. Краткое повторение или ссылка допустимы, если они помогают понять текущий контекст.

Ориентир:

```text
цель задачи        → TASK.md
текущее состояние  → WORKFLOW.md
общий контекст     → COMMUNICATION.md
решения            → DECISIONS.md
история            → HISTORY.md
ошибки агентов     → AGENT_ERRORS.md
личная память      → agents/
этап               → stages/
исследование       → research/
временная работа   → scratch/
```

## 8. Чтение служебного PR

Агент не обязан читать весь служебный PR.

Обычный вход:

```text
AGENTS.md
→ RULES.md
→ TASK.md
→ WORKFLOW.md
→ свой личный файл
→ материалы активной работы
```

`COMMUNICATION.md`, `DECISIONS.md`, результаты предыдущих этапов, `research/`, `HISTORY.md` и чужие личные файлы читаются в той мере, в которой они действительно нужны текущей задаче.

`WORKFLOW.md` должен позволять понять, какой дополнительный контекст необходим прямо сейчас.

## 9. Передача работы

Перед передачей агент приводит относящийся контекст в актуальное состояние.

Следующий агент должен получить достаточно информации, чтобы выполнить назначение без технического пересказа разработчиком.

Комментарии служебного PR используются только как короткий сигнал управления:

1. кто закончил;
2. кто следующий;
3. что ему назначено;
4. где находится актуальный контекст.

Подробные планы, исследования, findings и отчёты в комментарии не копируются. По возможности актуальный управляющий комментарий редактируется вместо создания нового.

## 10. После завершения работы

После завершения этапа или существенной подзадачи актуализируются только действительно затронутые рабочие файлы.

Значимый результат или событие сохраняется там, где оно понадобится дальше; устаревший оперативный и временный контекст убирается.

Главный принцип: служебный PR может хранить большой объём полезной информации, но агенту для конкретного следующего действия должен требоваться небольшой и понятный набор контекста.
