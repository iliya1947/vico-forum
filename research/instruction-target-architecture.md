# Минимальная целевая архитектура инструкций

Статус: целевая схема после inventory + classification + loss/conflict-check. Это ещё не финальная редакция текста и не команда применять изменения.

## 1. Принцип архитектуры

Правило должно находиться в самом высоком слое, где его область действия действительно нужна, **но только если при этом не теряется аудитория**.

Отсюда:

- **U — User instructions**: универсальное поведение ChatGPT во всех чатах и проектах.
- **P — Project instructions**: ChatGPT-правила, специфичные для Vico Forum и взаимодействия с Codex/разработчиком.
- **A — AGENTS.md**: общий repository contract для ChatGPT и Codex: роли, GitHub/workflow, review, technical diagnosis, project source-of-truth и shared-agent guards.
- Намеренный повтор между U и A допустим только когда он нужен **разным аудиториям**: U защищает ChatGPT вне проекта, A — Codex/shared agents внутри проекта.

Не вводить новую инструкцию, если она является только примером или частным случаем уже достаточного общего правила.

## 2. Целевой пользовательский слой U

### 2.1 Оставить текущие универсальные правила

Оставить по смыслу:

- U01 — обязательность пользовательских инструкций.
- U02 — отвечать по существу.
- U03 — не выдумывать факты.
- U04 — изменяемую техническую информацию проверять по актуальным первичным источникам и версии.
- U05 — явно обозначать существенную непроверенную информацию.
- U06 — не заявлять невыполненное чтение/проверку/действие; полное чтение означает фактическое чтение до конца.
- U07 — факты/условия отдельно от предположений и выводов; вывод без скрытых посылок; противоречия; пересмотр при изменении основания; предыдущая ошибка не становится фактом.
- U09 — актуальная цель; не первая трактовка автоматически; существенные альтернативы/последствия; самостоятельно выбранное действие должно быть обосновано и вести к цели; доступная диагностика до действий пользователя.
- U10 — однозначная задача выполняется без лишних вопросов.
- U11 — не добавлять ненужные инструкции/следующие шаги.
- U12 — приоритет точности, проверяемости, логики и практического результата.
- U14 — нумеровать списки.
- U15 — семантика `...`.

Важно: на этапе финальной редакции U07/U09 нельзя «сжимать» ещё сильнее. Наоборот, нужно проверить их исполнимость как составных правил и при необходимости **разделить**, а не склеивать. Метрика — не число пунктов, а число независимых требований и объём текста.

### 2.2 Удалить без замены

- U08 — прямой дубль U07.
- U13 — прямой дубль U07.

### 2.3 Добавить только шесть новых универсальных смыслов

**U-N1 — Permission boundary**
Наличие finding, корректного решения или технической возможности не создаёт разрешение на внешнее действие; разрешение действует только в установленной области.

**U-N2 — Decision authority**
Наличие информации, роль исполнителя/reviewer или техническая возможность не создают право принять принадлежащее другому решение.

**U-N3 — Evidence scope**
Масштаб вывода не должен превышать масштаб фактически применимого доказательства.

**U-N4 — Modality**
Не усиливать смысл утверждения: возможность, достаточность, рекомендация/default и разрешение не превращаются автоматически в обязательность, необходимость или требование.

**U-N5 — Stop condition**
Не продолжать анализ ради полной уверенности, если данных уже достаточно для обоснованного вывода/действия и оставшаяся неопределённость не способна существенно изменить результат.

**U-N6 — Applicability**
Факт, правило или источник применять только к тому объекту, версии, состоянию, времени и области, для которых он действительно применим.

### 2.4 Не добавлять отдельными пользовательскими правилами

Не создавать отдельные строки для:
- причинности из корреляции;
- ложной точности;
- denominator/double-count;
- baseline compatibility;
- false dichotomy/classification labels;
- обобщения единичного случая;
- разового исключения;
- same-level instruction precedence;
- порога каждого уточняющего вопроса;
- shared evidence нескольких агентов;
- отсутствия найденного объекта;
- stale conclusion;
- local optimization.

Причина: они уже покрываются U07/U09 + U-N1/U-N3/U-N5/U-N6 либо имеют конкретную project specialization.

## 3. Целевой проектный слой P

### 3.1 Оставить

- P01 — совместное действие пользовательских и проектных правил; текущая прямая команда разработчика сильнее project rule.
- P02 — bootstrap: получить актуальный `main` и полностью прочитать `AGENTS.md`.
- P03 — найденная в работе Codex проблема сначала классифицируется как current-Stage defect или future work.
- P04 — если обязательное правило невозможно выполнить, не выполнять противоречащее ему действие.
- P05–P13 — правила формирования задания Codex.
- P14–P16 — декомпозиция длительной работы и остановка после подзадачи.
- P17–P18 — стратегия риска до/после pre-release.

### 3.2 Удалить без замены

- P19 — «работать от цели»: полностью покрывается универсальным U09.
- P20 — «перед ответом сверить контекст / не брать первую трактовку»: полностью покрывается U09.

### 3.3 Не переносить в P

Не помещать сюда:
- GitHub/PR permissions;
- роли repository-агентов;
- CI/review workflow;
- exact-head semantics;
- technical diagnosis;
- source-of-truth project files.

Это A-level contract.

## 4. Целевой AGENTS.md слой A

### 4.1 Сохранить generic logic A-L1–A-L6 пока существует текущая аудитория

Несмотря на дублирование с U, A-L1–A-L6 пока оставить.

Причина: U защищает ChatGPT, а A-L1–A-L6 сейчас являются единственным repository-level generic reasoning coverage для Codex.

Это **намеренный дубль по аудитории**, а не кандидат на удаление.

Отдельная будущая оптимизация возможна только если появится гарантированный Codex-only источник этих guards. Создавать такой источник заранее сейчас не требуется.

### 4.2 Сохранить project/shared-agent sections

Сохранить:
- A-L7 — журналирование логических ошибок.
- Roles.
- Principles A-P1–A-P5.
- Technical diagnosis A-D.
- Fix scope A-F.
- Workflow A-W.
- Developer action A-DA.
- General A-G.
- PR test launch A-CI.
- PR review A-REV.
- Documentation audit A-AUD.

Их нельзя удалять только потому, что отдельные фразы напоминают U: они задают конкретные project contracts или обеспечивают Codex/shared-agent audience.

### 4.3 Единственный подтверждённый новый A-level contract

Нужен project-specific PR permission rule:

- агент не создаёт новый PR любого типа без прямого разрешения разработчика;
- агент не меняет назначенный служебный PR без прямой команды разработчика;
- разрешение выполнять задачу, работать с GitHub, изменять файлы, проверять или продолжать работу само по себе не является разрешением создать PR или сменить служебный PR.

Это не следует оставлять только на U-N1, потому что точный GitHub permission contract должен быть explicit в repository workflow.

До отдельной команды разработчика этот пункт остаётся **предложением**, а не изменением `AGENTS.md`.

## 5. Намеренные повторы, которые не считать мусором

### U04 ↔ A-G5
U04 нужен ChatGPT вообще; A-G5 нужен всем repository-агентам и конкретизирует official documentation.

### U05/U06 ↔ A-D6/A-G5/A-AUD
U задаёт универсальную честность ответа; A задаёт конкретные technical/audit obligations и Codex coverage.

### U07/U09 ↔ A-L1–A-L6
В текущей архитектуре повтор сохраняется из-за разной аудитории ChatGPT vs Codex/shared agents.

### U09/U10 ↔ A-D4/A-DA2
U регулирует универсальное взаимодействие ChatGPT с пользователем; A задаёт конкретный Vico workflow «сначала доступное действие агента».

## 6. Что реально уменьшается

Без механического переписывания можно удалить **четыре самостоятельных действующих правила**:

- U08;
- U13;
- P19;
- P20.

При этом добавляются шесть действительно новых универсальных guards U-N1…U-N6.

Следовательно, задача этой работы **не** в том, чтобы доказать, что новая версия обязательно будет короче старой пользовательской по числу пунктов. Цель — убрать мусорные дубли и добавить только те защиты, которых реально не хватало.

Дополнительное значимое уменьшение общего instruction load возможно только через отдельную работу над `AGENTS.md`:
- искать project-internal дубли между разделами;
- не удалять generic Codex guards без replacement;
- не переносить project workflow в U.

Это отдельный следующий этап, а не часть текущего U/P/A распределения.

## 7. Целевая зависимость слоёв

```text
User instructions (универсальный ChatGPT)
        ↓ применяются и в Vico
Project instructions (Vico-specific ChatGPT orchestration)
        ↓ bootstrap / routing
AGENTS.md (repository shared contract: ChatGPT + Codex)
        ↓
task/source-of-truth/service-PR local rules
```

Верхний слой не должен пересказывать нижний project workflow.
Нижний слой может намеренно повторять universal guard только если он нужен другой аудитории или конкретизирует исполнимый project contract.

## 8. Критерий готовности следующего этапа

Следующим этапом можно проектировать конкретные редакции только после отдельной проверки:

1. каждое новое U-N1…U-N6 выражается коротко и атомарно;
2. U07/U09 не превращаются в ещё более длинные «суперпункты»;
3. удаление U08/U13/P19/P20 действительно не меняет поведение;
4. предложенный A-level PR permission contract не конфликтует с existing service/implementation PR workflow;
5. никакие изменения не применяются без отдельной прямой команды разработчика.
