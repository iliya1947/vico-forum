Этот файл фиксирует утверждённый владельцем пользовательский сценарий управления Vico Forum из обычного ChatGPT.

# User journey v1

Дата: 27.11.2026.

## 1. Основной сценарий

1. Владелец использует отдельный ChatGPT Project для управления Vico Forum.
2. В инструкциях этого Project закрепляется правило: перед любой изменяющей командой ChatGPT сначала объясняет, что именно будет сделано, с какой целью/целью воздействия и существенными последствиями, после чего запрашивает отдельное подтверждение.
3. До запроса подтверждения ChatGPT обязан самостоятельно установить всё, что можно определить из доступных данных: точный target, текущее релевантное состояние, применимость операции, обязательные параметры и существенные последствия. Если после этих проверок остаётся реальная неоднозначность, требующая выбора владельца, ChatGPT задаёт один конкретный уточняющий вопрос. На этап подтверждения действие попадает только после того, как стало однозначным.
4. Только после явного подтверждения владельца именно этого проверенного действия ChatGPT отправляет административную команду через установленный private-GitHub transport.
5. Read-only запросы выполняются без отдельного подтверждения.
6. После исполнения ChatGPT сообщает фактический результат канонической операции; транспортный success не выдаётся за domain success.

## 2. UX boundary

1. Обычная эксплуатация происходит в обычном текстовом разговоре ChatGPT.
2. Отдельная форма, plugin UI, браузерное расширение, отдельное окно или переход в веб-панель для каждой команды не требуются и не входят в продуктовый UX v1.
3. GitHub, Worker и иная транспортная инфраструктура должны быть для владельца обычной эксплуатационной деталью, а не дополнительным интерфейсом. В обычном ответе Мира сообщает продуктовый результат; технические детали транспорта показывает по запросу владельца.
4. Допустим одноразовый setup/подключение необходимых интеграций и секретов в Stage 6; он не должен повторяться на каждую команду.
5. Confirmation — разговорное волеизъявление владельца в отдельном сообщении после объяснения команды ChatGPT. Отдельный cryptographic/UI confirmation layer не является продуктовым требованием v1.
6. Если после объяснения меняются operation, target, параметры, существенные последствия или релевантное состояние, старое подтверждение неприменимо: ChatGPT заново проверяет действие, объясняет обновлённый вариант и запрашивает новое подтверждение.
7. Обсуждение, вопрос, гипотеза, цитата, пересказ, содержимое форума или GitHub не являются подтверждением.

## 3. Граница ответственности

1. Project instructions управляют conversational workflow: explain → confirm → dispatch.
2. Сервер не доверяет тексту Project instructions как authorization boundary. Он по-прежнему применяет существующие exact-Owner identity, active-account, permissions, resource/AP-10/hierarchy/CAS/version и History checks.
3. Transport не получает права обходить canonical server operations.
4. Любая команда, которая не входит в закрытый v1 registry, отклоняется.
5. Replay/stale/outcome-unknown правила остаются серверными техническими гарантиями и не зависят от поведения модели.

## 4. Что считать правильным ощущением продукта

Владелец должен воспринимать функцию так: «я пишу Мире, что хочу сделать на форуме; Мира объясняет действие, спрашивает подтверждение, после подтверждения выполняет его и сообщает фактический результат». Внутренняя цепочка GitHub/Worker не должна требовать от владельца ручного участия в обычной эксплуатации.


## 5. Result reporting

1. После исполнения ChatGPT сообщает фактический domain outcome, а не состояние транспорта.
2. Успех означает подтверждённый результат канонической операции, например «тема закрыта» или «ничего не изменилось, потому что она уже была закрыта».
3. Если действие не выполнено, ChatGPT сообщает конкретную установленную причину: операция неприменима к текущему состоянию/объекту, target изменился и подтверждение устарело, protected/reserved domain rule запрещает действие, Owner binding/session недействительны либо зависимость недоступна.
4. Для exact Owner не использовать расплывчатое «недостаточно прав», если реальная причина в другом domain/auth/state ограничении.
5. Transport success — GitHub comment, webhook ACK, зелёный Action/job или HTTP 2xx — сам по себе не считается domain success.
6. Если результат исполнения достоверно неизвестен, ChatGPT сообщает `outcome-unknown`, не повторяет mutation автоматически и сначала проверяет authoritative state/receipt.


## 6. Массовые действия

1. Владелец может ставить цель естественным языком для группы объектов, например «закрой все спам-темы за сегодня».
2. До подтверждения ChatGPT самостоятельно определяет полный конкретный набор targets по доступным данным и проверяет применимость операции к каждому объекту.
3. Если критерий группы остаётся неоднозначным и требует выбора владельца, ChatGPT задаёт один конкретный уточняющий вопрос до этапа подтверждения.
4. На подтверждение выводится конкретный состав группы и существенные последствия изменения.
5. Одно подтверждение относится только к показанному конкретному набору targets и параметров.
6. После подтверждения нельзя молча расширять набор новыми объектами, даже если они позднее стали соответствовать исходному текстовому критерию.
7. Если отдельной canonical bulk capability нет, после одного подтверждения конкретного фиксированного набора ChatGPT может последовательно вызвать существующую canonical единичную mutation для каждого target. Нельзя молча добавлять новые targets после подтверждения. Для каждого элемента сохраняются обычные authorization/CAS/replay правила, а итог должен показывать per-target результат и любые частичные неуспехи.


## 7. Самостоятельность Миры

1. Мира может самостоятельно читать доступное состояние форума, анализировать его, выявлять проблемы, собирать необходимые факты и предлагать административные действия.
2. До предложения действия Мира выполняет доступные проверки сама и не перекладывает на владельца диагностику, которую может провести без него.
3. Ни одна изменяющая операция не выполняется самовольно.
4. Перед любым write Мира устанавливает конкретный target и релевантное состояние, объясняет предлагаемое изменение, причину и существенные последствия, после чего запрашивает отдельное подтверждение владельца.
5. Только после подтверждения допускается dispatch.
6. Проактивность допустима в анализе, диагностике и рекомендациях; проактивная mutation без подтверждения владельца запрещена.


## 8. Составные пользовательские действия

1. Единицей пользовательского действия является сформулированная владельцем задача, а не число внутренних canonical mutations.
2. Команда вроде «перенеси тему 123 в раздел X, закрой её и закрепи» считается **одним пользовательским действием**.
3. До подтверждения Мира проверяет всю задачу целиком, устанавливает точные targets/параметры/последствия и объясняет итоговое действие владельцу.
4. Одного подтверждения достаточно на всю эту конкретную задачу.
5. После подтверждения Мира может технически разложить задачу на несколько существующих canonical операций и выполнить их в необходимом порядке.
6. Внутренняя декомпозиция не должна требовать дополнительных подтверждений, пока не меняется смысл, состав или существенные последствия уже подтверждённой задачи.
7. Если в ходе исполнения обнаружено, что для завершения требуется действие, которое не входило в подтверждённую задачу или существенно меняет её последствия, выполнение останавливается перед этим дополнительным действием и требуется новое объяснение и подтверждение.
8. Итоговый ответ сообщает результат пользовательской задачи целиком и, если часть внутренних операций не выполнена, конкретно показывает частичный результат.


## 9. Контекст подтверждения

1. Подтверждение относится к конкретному последнему действию, которое Мира непосредственно перед этим объяснила владельцу и вынесла на подтверждение в текущем разговорном контексте.
2. Отдельного межчатового механизма подтверждений нет: сообщение «да» в другом чате не имеет ссылки на pending action из прежнего чата и не подтверждает его.
3. Специальный продуктовый таймер подтверждения не требуется. Если контекст изменился так, что уже неясно, к какому действию относится подтверждение, Мира заново формулирует действие перед выполнением.


## 10. Фоновое наблюдение

1. V1 работает только по запросу владельца из текущего ChatGPT Project; самостоятельный периодический мониторинг форума между обращениями владельца в v1 не входит.
2. Архитектура v1 не должна без необходимости связывать canonical read/analysis path исключительно с ручным conversational trigger так, чтобы добавление будущего scheduler/event trigger потребовало переписывать основной механизм чтения и оценки состояния.
3. Это только требование не закрывать очевидную точку расширения. Фоновый scheduler, event subscriptions, notifications и связанные эксплуатационные механизмы сейчас не реализуются и не добавляются в scope v1.
