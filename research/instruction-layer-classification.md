# Классификация правил по слоям

Статус: аналитическое решение по размещению; действующие инструкции пока не изменяются.

## 1. Критерий классификации

Используются четыре слоя решений:

- **KEEP** — правило уже находится в правильном слое.
- **MOVE-UP** — универсальная мыслительная защита должна находиться в пользовательских инструкциях ChatGPT, а нижний общий дубль после этого можно удалить.
- **KEEP-SPECIALIZATION** — верхнее универсальное правило и нижнее проектное правило нужны одновременно, потому что нижнее задаёт конкретный проектный контракт/процедуру, а не повторяет общий принцип.
- **DELETE-DUPLICATE** — правило не даёт отдельной защиты в своём слое.
- **NO-NEW-RULE** — найденный кандидат является частным случаем уже достаточного общего правила и отдельной строки не требует.

Важное ограничение: пользовательские инструкции применяются к ChatGPT во всех контекстах; проектные инструкции — к ChatGPT в Vico Forum; `AGENTS.md` — общий репозиторный регламент ChatGPT и Codex. Поэтому удаление универсальной логики из `AGENTS.md` означает, что Codex перестанет получать именно эту общую мыслительную подсказку. Это осознанное следствие ранее принятого подхода: Codex-specific user instructions пока не заполняются до появления реальной необходимости.

## 4. `AGENTS.md`: generic logic против project workflow

### 4.1 Generic logic A-L1–A-L6

Решение: **MOVE-UP → U, затем удалить generic-дубль из A**.

Причина:
- эти пункты не Vico-specific: цель, факты/предположения, альтернативы, скрытые посылки, связь действия с целью и пересмотр выводов;
- для ChatGPT они должны работать во всех чатах;
- большая часть уже присутствует в U07/U09;
- сохранение того же блока одновременно в U и A увеличивает инструкционный шум для ChatGPT.

Следствие:
- Codex после удаления A-L1–A-L6 не будет получать эти generic мыслительные подсказки из репозитория;
- это не компенсируется сейчас отдельными Codex user instructions, поскольку разработчик ранее решил не добавлять их заранее;
- конкретные технические/процессные защиты Codex остаются в A-D, A-F, A-W, A-REV и других project-specific разделах.

### 4.2 A-L7 журналирование логических ошибок

Решение: **KEEP**.

Это repository-specific operational rule, а не универсальная логика.

### 4.3 A-P принципы работы агентов

- A-P1 «думай своей головой» — **KEEP**: командная семантика работы с выводами других агентов.
- A-P2 взаимные проверки — **KEEP**: project/team workflow.
- A-P3 смотреть шире поручения — **KEEP**: project agent behavior и scope awareness.
- A-P4 проактивно использовать возможности инструментов — **KEEP**: project workflow.
- A-P5 не перепроверять без причины — **KEEP**: project efficiency contract; отдельное universal U-правило пока не требуется.

### 4.4 A-D диагностика

Решение: **KEEP-SPECIALIZATION**.

Даже если U сохраняет общий принцип «сначала доступная диагностика», A-D задаёт технически специфичный контракт: симптомы, ожидаемое поведение, causal chain, альтернативные причины, штатный путь, workaround, достаточность данных. Это не просто дубль.

### 4.5 A-F масштаб исправления

Решение: **KEEP**.

Это Vico-specific engineering policy, а не универсальная пользовательская логика.

### 4.6 A-W / A-DA / A-G / A-CI / A-REV / A-AUD

Решение: в основном **KEEP** как project/repository workflow.

Исключения:
- A-G5 про официальную документацию сохраняется как **KEEP-SPECIALIZATION** относительно U04, потому что нужен всем repository-агентам и задаёт проектную обязанность;
- A-G2/A-AUD полное чтение сохраняются как **KEEP-SPECIALIZATION** относительно U06, потому что определяют конкретный обязательный scope чтения;
- A-REV5 Stage/future classification остаётся и позволяет удалить P03;
- A-DA2 «если шаг доступен агенту, выполнить самому» остаётся как workflow specialization относительно U09/U10.

## 6. Конкретный project-specific пробел, который нельзя решать только пользовательской логикой

Текущий A-R3 запрещает Мире менять назначенный служебный PR без прямой команды, но не формулирует общий запрет создавать новый PR любого типа без прямого разрешения разработчика.

Классификация: **A-level project permission rule**, не U-level.

Причина: это конкретный GitHub/Vico contract. Универсальный C01 нужен как мыслительная защита, но он не должен заменять точное project permission правило.

На этом этапе правило не редактируется; фиксируется только правильный слой.

## 7. Что реально можно удалить без потери отдельной защиты

Подтверждённый список на текущем этапе:

1. U08 — прямой дубль U07.
2. U13 — прямой дубль U07.
3. P03 — дублируется более общим A-REV5.
4. P19 — дублируется универсальным U09.
5. P20 — дублируется универсальным U09.
6. После переноса/проверки универсальных смыслов в U — generic A-L1–A-L6.
7. Большинство C-кандидатов не превращать в отдельные инструкции: C04, C07–C17 (кроме C18 как уже существующего смысла) и C19 поглощаются более общими правилами или project specializations.

## 8. Что действительно требует новой верхнеуровневой защиты

Минимальный новый набор после классификации:

1. C01 — границы разрешения; finding/fix не создаёт permission.
2. C02 — полномочие на решение отдельно от знания/исполнения.
3. C03 — масштаб вывода не превышает масштаб доказательства.
4. C05 — не усиливать модальность утверждения.
5. C06 — прекращать анализ при достаточности данных.

Это **пять** новых универсальных смыслов, а не весь список из десятков стресс-тестов.

## 9. Итог этапа

Ключевой результат: оптимизация должна идти не от «55 → 31 → 11», а от семантических владельцев.

- Universal ChatGPT thinking → U.
- ChatGPT orchestration внутри Vico → P.
- Repository/GitHub/team/Codex workflow → A.
- Частный пример общей логической ошибки → журнал/история, а не новая инструкция.

Следующий этап — проверить эти классификации на конфликт и достаточность: если удалить отмеченные дубли и оставить только пять новых универсальных защит, не исчезнет ли какая-либо реально требуемая защита.
