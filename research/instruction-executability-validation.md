# Проверка целевой архитектуры на исполнимость

Статус: проверка `instruction-target-architecture.md` на реальную исполнимость и instruction load. Действующие инструкции не изменяются.

## 1. Итог

Целевая архитектура **не готова к прямому превращению в редакцию**.

Причина: она правильно распределила смысл по слоям, но всё ещё:
- увеличивает пользовательский слой с 15 до 19 пунктов по простой арифметике `15 - U08 - U13 + 6 новых guards`;
- оставляет U07 и U09 составными «суперпунктами»;
- не снимает неоднозначность между «выполняй без лишних вопросов» / `...` и отдельным permission boundary;
- почти не уменьшает общий ChatGPT instruction load, потому что generic A-L1–A-L6 остаются в `AGENTS.md` ради Codex.

Следовательно, переход сразу к финальной редакции U/P/A был бы преждевременным.

## 2. U07 — FAIL как текущая исполнимая единица

U07 одновременно содержит:
1. отделение фактов/условий от предположений/выводов;
2. hidden-premise check;
3. contradiction check;
4. пересмотр зависимых выводов при изменении основания;
5. запрет переносить ошибку предыдущего ответа как факт.

Это пять независимых мыслительных операций.

Вывод: U07 нельзя оставлять как один instruction unit и нельзя ещё сильнее уплотнять. При финальном проектировании его нужно переразложить на минимальные атомарные guards и одновременно использовать это переразложение для поглощения части новых C-кандидатов.

## 3. U09 — FAIL как текущая исполнимая единица

U09 одновременно требует:
1. установить текущую цель/смысл;
2. не принять первую трактовку;
3. проверить альтернативы;
4. проверить существенные последствия;
5. проверить обоснованность самостоятельно выбранного действия;
6. проверить связь действия с целью;
7. выполнить доступную диагностику до действий пользователя;
8. не вести пользователя пробами и ошибками.

Это слишком много операций для одного пункта.

Вывод: U09 должен быть не «сжат», а разложен по двум-трём смысловым блокам.

## 4. U-N3 + U-N6 — можно объединить без потери атомарности

Предыдущая архитектура считала отдельными:
- U-N3: масштаб вывода ≤ масштаб доказательства;
- U-N6: источник/факт применим только к соответствующему объекту/версии/состоянию.

Проверка показывает общий логический объект: **применимое доказательство**.

Корректный единый guard по смыслу:

> Вывод должен опираться только на доказательства, применимые к текущему объекту/версии/состоянию, и не выходить за пределы фактически подтверждённого ими объёма.

Это не механическое склеивание разных требований: применимость определяет, какие данные вообще входят в evidence set, а scope ограничивает вывод по этому же evidence set.

Решение: считать C03 + C11 **одним новым evidence guard**.

Число действительно новых U-смыслов уменьшается с 6 до **5**.

## 5. U-N1 и U-N2 — НЕ объединять

- U-N1: permission на внешнее действие.
- U-N2: authority принять решение.

Они связаны, но не эквивалентны.

Можно иметь permission выполнить действие без права выбрать, какое действие должно быть выполнено; можно иметь authority выбрать решение, но не иметь permission самостоятельно выполнить внешнее изменение.

Решение: оставить раздельными.

## 6. U-N4 — оставить отдельным

Modality error не сводится надёжно к hidden-premise check на практике.

Короткий отдельный guard оправдан реальными ошибками:
- default → mandatory;
- allowed → required;
- possible → established/necessary.

## 7. U-N5 — оставить отдельным

Stop condition нужен отдельно, потому что этот чат подтвердил runaway-analysis failure.

Он не конфликтует с требованием думать глубоко: останавливается только анализ, остаточная неопределённость которого уже не способна существенно изменить результат.

## 8. Конфликт U10 / U15 с permission boundary

### U10
Текущее: «Если задача однозначна — выполняй без лишних вопросов».

Без уточнения это может быть прочитано как:
- задача ясна;
- значит действие разрешено.

Это неверно.

U10 должен сохранять смысл «не спрашивать лишнего», но **не быть источником permission**.

### U15
Текущее значение `...`: продолжить следующий очевидный шаг самостоятельно.

Здесь тот же риск: `...` может ошибочно интерпретироваться как blanket permission на любое новое внешнее действие.

Правильная семантика:
- `...` разрешает продолжение уже установленной текущей задачи;
- не расширяет её scope;
- не создаёт новых полномочий/разрешений, которых раньше не было.

Это не новый guard, а необходимое уточнение самой команды `...`.

## 9. U-N1 снимает потенциальный конфликт U09 ↔ A-P3

A-P3 требует «смотреть шире непосредственного поручения».

Без permission boundary агент может перейти:
`заметил соседнюю проблему → решил, что надо исправить → исправил`.

С U-N1 семантика становится:
`заметил → оценил влияние → сообщил/учёл в допустимой мере`;
исправление требует собственного основания и разрешения.

PASS.

## 10. Stop condition C06 ↔ Project P14–P16

Конфликта нет.

- C06 говорит, когда прекратить дальнейший **анализ** как не влияющий на решение.
- P14–P16 говорят, когда остановить **длительную работу после завершённой подзадачи** и отчитаться разработчику.

Это разные уровни управления.

PASS.

## 11. A-level PR permission proposal ↔ существующий workflow

Потенциальный конфликт существует только при неудачной формулировке.

`AGENTS.md` сейчас говорит, что:
- для отдельной задачи используется служебный PR;
- для bounded implementation используются implementation PR.

Это определяет **структуру работы**, но может быть ошибочно прочитано как implicit permission создавать эти PR.

Новый contract совместим с workflow, если явно устанавливает:
- workflow описывает, **какой PR нужен после получения разрешения**;
- само наличие workflow или назначенной задачи **не является разрешением создать PR**.

Таким образом стандартный процесс не ломается, но появляется явный developer gate.

PASS при такой семантике.

## 12. Главный unresolved load issue — AGENTS.md

Даже после очистки U/P общий ChatGPT instruction load заметно не уменьшится, потому что:
- U будет содержать универсальную reasoning-логику;
- A-L1–A-L6 останутся ради Codex;
- ChatGPT в Vico будет видеть оба слоя.

Удалить A-L1–A-L6 нельзя без потери Codex coverage.

Следовательно, дальнейшее реальное сокращение требует **внутреннего аудита AGENTS.md**, а не ещё одной попытки ужать User instructions.

Нужно проверить:
- дубли A-L ↔ A-P ↔ A-D ↔ A-REV;
- повторение permission/scope semantics между Roles, Workflow, General и Review;
- повторение full-read/verification semantics;
- можно ли сократить project wording без удаления Codex guards;
- какие rules являются general reasoning, а какие реально workflow-specific.

Это следующий необходимый этап до финальных редакций.

## 13. Исправленная целевая математика U

На этом этапе нельзя честно назвать финальное число пунктов, пока U07/U09 не переразложены.

Но подтверждено:
- удалить 2 прямых U-дубля;
- добавить не 6, а **5** новых самостоятельных смыслов;
- часть новых смыслов может занять место внутри переразложенной epistemic/action architecture, а не просто добавиться к существующим 13 оставшимся пунктам.

Поэтому формула `15 - 2 + 6 = 19` **отменена как целевая модель**.

## 14. Решение этапа

1. Не переходить ещё к финальной редакции U/P/A.
2. Считать C03+C11 одним evidence/applicability guard.
3. U-N1, U-N2, U-N4, U-N5 оставить самостоятельными.
4. U10 и U15 в будущей редакции явно не должны создавать permission.
5. Перед финальными редакциями выполнить внутренний аудит `AGENTS.md` на реальные дубли и instruction load.
6. Действующие инструкции пока не менять.
