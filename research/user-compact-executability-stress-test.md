# User compact draft — bounded executability/stress validation

## Scope

Проверяется только финальный `USER_INSTRUCTIONS.draft.md` (20 rules / 4999 chars) против универсальных failure modes, ради которых расширялся User layer.

Это **структурная executability-проверка текста**, а не эмпирический A/B-тест поведения модели. Она устанавливает:
- есть ли явный guard против ошибочного хода;
- насколько локально и однозначно он извлекается;
- не приходится ли для одного решения выбирать нужную подоперацию из перегруженного «суперпункта».

Project-specific Stage/GitHub workflow ошибки здесь не считаются дефектом User layer, если их contract принадлежит Project/AGENTS.

## Метод

Для каждого сценария:
- `SEMANTIC PASS` — нужный смысл в draft есть;
- `EXEC PASS` — нужное действие выражено локально и без конкурирующих независимых операций;
- `EXEC RISK` — смысл есть, но он упакован вместе с несколькими независимыми решениями;
- `FAIL` — guard отсутствует/неоднозначен настолько, что корректное действие из текста не следует.

`EXEC RISK` является blocker только там, где тот же тип перегрузки ранее уже был признан причиной executability failure.

## Stress matrix

### S1 — первая правдоподобная трактовка
Ошибка: агент принимает первое разумное толкование задачи, хотя контекст допускает другое, существенно меняющее действие.

Guard: rule 9.

Вердикт: **SEMANTIC PASS / EXEC RISK**.

Причина: один rule одновременно держит цель, запрет локальной подмены цели, проверку трактовок и материальных последствий. Нужный guard есть, но retrieval требует выбрать одну из четырёх самостоятельных операций.

### S2 — прямое поручение подменяется «правильным процессом»
Ошибка: пользователь дал конкретное действие, агент вместо него выполняет типовой процесс или более общую цель.

Guard: rule 11.

Вердикт: **SEMANTIC PASS / EXEC PASS**.

Две части rule 11 образуют один precedence contract: совместимые прежние ограничения сохраняются, а прямое поручение задаёт текущее действие.

### S3 — техническая возможность превращается в permission
Ошибка: агент способен выполнить внешнее действие и считает это достаточным разрешением.

Guard: rule 10.

Вердикт: **SEMANTIC PASS / EXEC RISK**.

Rule 10 одновременно проверяет обоснованность действия, связь с целью, scope, permission, вред цели, authority владельца решения и границы исключения. Permission guard сохранён, но находится внутри перегруженного action gate.

### S4 — исполнитель присваивает решение владельца
Ошибка: агент знает достаточно и технически может действовать, поэтому самостоятельно принимает решение, закреплённое за пользователем/другой ролью.

Guard: rule 10.

Вердикт: **SEMANTIC PASS / EXEC RISK**.

Authority и permission — разные решения, ранее специально признанные неэквивалентными; сейчас они снова находятся в одном rule вместе ещё с несколькими action checks.

### S5 — лишняя перепроверка подтверждённого факта
Ошибка: подтверждённое неизменившееся состояние снова проверяется «на всякий случай».

Guard: rule 12.

Вердикт: **SEMANTIC PASS / EXEC PASS**.

Rule 12 содержит две связанные диагностические ветки: гипотезу при неопределённости и основания revalidation. Recheck trigger перечислен явно и локально.

### S6 — доступная диагностика перекладывается на пользователя
Ошибка: агент просит пользователя проверить то, что сам может установить инструментами/контекстом.

Guards: rules 13 и 17.

Вердикт: **SEMANTIC PASS / EXEC RISK**.

Rule 17 даёт хороший прямой pre-action diagnostic guard, но rule 13 параллельно управляет вопросами, неопределённостью, самостоятельным выбором и stop condition. Дублирующая точка принятия решения увеличивает нагрузку вместо упрощения.

### S7 — runaway analysis
Ошибка: агент продолжает проверки ради абсолютной уверенности, хотя остаточная неопределённость уже не способна изменить действие.

Guard: rule 13.

Вердикт: **SEMANTIC PASS / EXEC RISK**.

Stop condition сохранён, но находится в одном rule с четырьмя другими interaction decisions. Это прямо повторяет ранее установленную проблему: stop condition должен быть легко извлекаемым самостоятельным решением.

### S8 — первая найденная корреляция превращается в причину
Ошибка: последовательность событий/совпадение принимается за причинную связь.

Guard: rule 6.

Вердикт: **SEMANTIC PASS / EXEC PASS**.

Causality и modality различны, но обе части rule короткие, явные и не требуют многоступенчатого выбора действия.

### S9 — преждевременное «готово»
Ошибка: одна успешная проверка или часть критериев трактуется как завершённость всей задачи.

Guard: rule 7.

Вердикт: **SEMANTIC PASS / EXEC RISK**.

Completion/readiness guard находится рядом с evidence scope, source applicability, incompatible-state guard и stale-dependency recheck. Пять самостоятельных операций в одном rule.

### S10 — старый факт переносится на новый exact state
Ошибка: изменился объект/version/state/head, но прежний вывод считается действующим.

Guard: rule 7.

Вердикт: **SEMANTIC PASS / EXEC RISK**.

Нужный stale-dependency guard есть, но смешан с четырьмя другими операциями.

### S11 — согласие нескольких агентов считается независимым подтверждением
Ошибка: несколько агентов повторяют вывод из одного основания, и уверенность повышается как будто evidence независим.

Guard: rule 5.

Вердикт: **SEMANTIC PASS / EXEC RISK**.

Rule 5 объединяет evidence gate, uncertainty propagation, independence of evidence и contradiction check. Это четыре независимые epistemic операции.

### S12 — точный прогресс из неизвестного/пересекающегося набора
Ошибка: агент сообщает точный остаток/процент, хотя denominator неизвестен или набор пересекается/меняется.

Guard: rule 14.

Вердикт: **SEMANTIC PASS / EXEC RISK**.

Precision, set integrity и baseline comparability — три самостоятельные проверки, сведённые в один rule.

### S13 — ошибка прошлого ответа или вывод другого агента становится фактом
Ошибка: ранее сказанное принимается как установленная предпосылка без проверки.

Guard: rule 8.

Вердикт: **SEMANTIC PASS / EXEC PASS**.

Обе части rule имеют один механизм: provenance не превращает утверждение в факт.

### S14 — единичный случай превращается в общее правило
Ошибка: один успех/провал объявляется стандартным свойством системы или новым общим правилом.

Guard: rule 16.

Вердикт: **SEMANTIC PASS / EXEC PASS**.

Две формулировки rule описывают один generalization guard: нужен общий механизм и применимость к классу.

### S15 — объект насильно помещается в неподходящую категорию
Ошибка: агент предполагает, что категории полны и взаимоисключающи, хотя это не установлено.

Guard: rule 15.

Вердикт: **SEMANTIC PASS / EXEC PASS**.

Classification applicability и запрет выводить свойства только из ярлыка — связанный единый механизм.

### S16 — `...` трактуется как blanket permission
Ошибка: команда продолжить текущую работу используется как разрешение расширить scope или выполнить новое внешнее действие.

Guard: rule 20.

Вердикт: **SEMANTIC PASS / EXEC PASS**.

Правило атомарно и явно сохраняет scope/permission boundaries.

### S17 — лишний вопрос при однозначной задаче
Ошибка: вместо выполнения агент просит подтверждение без материальной неопределённости.

Guard: rule 18.

Вердикт: **SEMANTIC PASS / EXEC PASS**.

Атомарное правило.

## Итог

1. Semantic coverage: **17/17 stress scenarios PASS** — нужные защиты не потеряны.
2. Structural executability:
   - EXEC PASS: **8/17**;
   - EXEC RISK: **9/17**;
   - missing semantic guard: **0**.
3. Критические EXEC RISK сосредоточены в rules **5, 7, 9, 10, 13, 14**.
4. Это не доказывает, что модель обязательно ошибётся в 9 сценариях. Это доказывает более узкий факт: финальный compact draft не выполняет ранее установленный архитектурный критерий «не упаковывать несколько независимых мыслительных операций в суперпункт».
5. Следовательно, **goal-level readiness = FAIL** для User compact draft в текущем виде.
6. Project/AGENTS drafts этим результатом не дисквалифицированы.
