# Recheck исходной цели после transfer-readiness

## Цель проверки

Transfer-readiness проверял вместимость, semantic coverage и отсутствие конфликтов между слоями. Эта проверка отдельно сверяет финальные drafts с исходной целью задачи: уменьшить когнитивную нагрузку и число тупых решений агентов, а не только сохранить все смыслы и уложиться в лимиты.

Исходные критерии уже были зафиксированы в `research/instruction-executability-validation.md`:
- не превращать несколько независимых мыслительных операций в один «суперпункт»;
- U07/U09 в прежнем виде были признаны FAIL именно по исполнимости;
- финальная редакция должна уменьшать instruction load без потери защит;
- permission/authority/stop-condition должны оставаться исполнимыми, а не растворяться в длинных составных правилах.

## Проверка финального User draft

Финальный `USER_INSTRUCTIONS.draft.md` имеет 20 пунктов / 4999 символов и сохраняет 52/52 semantic guards, но compact rewrite снова упаковал несколько независимых операций в составные пункты.

Подтверждённые примеры:

1. Rule 5 одновременно требует:
   - evidence gate;
   - propagation неопределённости;
   - различения независимых/зависимых подтверждений;
   - contradiction check.

2. Rule 7 одновременно требует:
   - evidence/applicability scope;
   - completion/readiness criteria;
   - запрет смешивать несовместимые состояния;
   - пересмотр зависимых выводов после изменения основания.

3. Rule 9 одновременно требует:
   - установить цель;
   - проверить материальные трактовки;
   - проверить материальные последствия.

4. Rule 10 одновременно требует:
   - обосновать самостоятельное действие;
   - проверить scope/permission;
   - не присваивать decision authority;
   - ограничивать permission/exception установленными границами.

5. Rule 13 одновременно требует:
   - самостоятельно установить доступную информацию;
   - продолжать при несущественной неопределённости;
   - самостоятельно выбирать между несущественными допустимыми вариантами;
   - определить, когда нужен вопрос пользователю;
   - применить stop condition и действовать при достаточности данных.

6. Rule 14 одновременно требует:
   - не завышать точность;
   - корректно считать прогресс/denominator/double-count;
   - проверять сопоставимость baseline.

Это не semantic loss: смыслы сохранены. Проблема другая — **executability/cognitive-load regression** относительно ранее принятого критерия.

## Остальные слои

1. `PROJECT_INSTRUCTIONS.draft.md` соответствует исходной архитектурной цели: project-specific правила отделены от universal reasoning и repository workflow; явного нового blocker на этой проверке не найдено.

2. `AGENTS.draft.md` сохраняет отдельные sections Logic / Principles / Diagnosis / Fix scope / Workflow / Review и Codex/shared-agent coverage. На этой проверке не найдено основания отменять его прежний PASS.

3. Следовательно, текущий blocker локализован в финальном compact User layer и возник после принудительного сжатия 8364 → 4999 символов.

## Вердикт

1. Предыдущий transfer-readiness PASS остаётся верным только в узком смысле:
   - лимиты;
   - semantic coverage;
   - межслойные конфликты.

2. Он **не доказывает достижение исходной behavioural/executability цели**.

3. Финальный User draft нельзя считать готовым к фактическому переносу, пока не выполнена отдельная executability/stress-проверка compact 20-rule версии против исходных failure modes.

4. Transfer package преждевременен.

## Следующий этап

Провести bounded executability/stress validation именно `USER_INSTRUCTIONS.draft.md` 20-rule / 4999-char версии:
- проверить типовые реальные failure modes, из-за которых началась переделка;
- установить, достаточно ли составных правил для устойчивого исполнения;
- если нет — перераспределить/упростить guards без выхода за 5000 символов и без semantic loss;
- после этого повторить goal-level readiness.
