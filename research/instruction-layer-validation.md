# Проверка классификации на потерю защиты и конфликты

Статус: корректирующий loss/conflict-check после `instruction-layer-classification.md`. Действующие инструкции не изменяются.

## 1. Критерий

Удаление или перенос правила допустимы только если:

1. его фактическая область действия полностью сохраняется;
2. все агенты, которым оно было нужно, продолжают получать эквивалентную защиту;
3. более общее правило действительно покрывает частный случай без скрытой посылки;
4. новое размещение не создаёт конфликт приоритетов или неявный перенос полномочий;
5. сокращение уменьшает реальный инструкционный объём, а не только число пунктов.

## 2. Проверка предложенных удалений

### U08 → DELETE-DUPLICATE — PASS

U08 повторяет две уже содержащиеся в U07 обязанности: вывод только из установленных фактов/условий и проверка противоречий. Отдельной области действия нет.

### U13 → DELETE-DUPLICATE — PASS

U13 буквально повторяет последнюю защиту U07 про ошибку предыдущего ответа. Удаление безопасно.

### P19 → DELETE-DUPLICATE — PASS

P19 «работать от цели» полностью покрывается U09, а U по прямому пользовательскому правилу действует и в проектах. Специфичной Vico/Codex семантики P19 не добавляет.

### P20 → DELETE-DUPLICATE — PASS

P20 «сверить текущий контекст / не брать первую трактовку» покрывается U09. Специфичной Vico-семантики нет.

### P03 → DELETE-DUPLICATE — FAIL

Предыдущее решение было ошибочным.

Причина: P03 применяется к **каждой проблеме, найденной ChatGPT в работе Codex**, независимо от того, находится ли агент в формальном PR-review. A-REV5 находится внутри раздела «Проверка PR» и формально регулирует findings этого review-процесса.

Следовательно, удаление P03 сузило бы область защиты.

Исправленное решение: **KEEP P03**, пока его более широкая семантика не будет явно перенесена в общий repository-level contract. На текущем этапе перенос не нужен.

## 3. Generic A-L1–A-L6 и Codex

Предыдущее решение: MOVE-UP в U и затем удалить из A.

Результат loss-check: **FAIL как автоматическое удаление**.

Факты:

- U применяется к ChatGPT.
- `AGENTS.md` является общим регламентом ChatGPT и Codex.
- Codex-specific user instructions по решению разработчика пока остаются пустыми.
- A-L1–A-L6 содержат generic reasoning protections, которыми сейчас пользуются оба класса агентов.

Если удалить A-L1–A-L6 после усиления U, ChatGPT сохранит защиту, а Codex — потеряет её.

Исправленное решение:

- **не удалять A-L1–A-L6 автоматически**;
- считать их текущим Codex/shared-agent coverage;
- вопрос их сокращения решать только если появится другое гарантированное место, откуда Codex получает те же необходимые защиты, либо если фактически будет установлено, что эти guards Codex не нужны.

Это означает, что часть дублирования U↔A для ChatGPT пока является **KEEP-DUPLICATE-BY-AUDIENCE**, а не ошибочным дублем.

## 4. Проверка пяти выбранных новых U-защит

### C01 — finding/fix ≠ permission; границы разрешения — PASS

Отдельная защита нужна.

U09 проверяет обоснованность действия и связь с целью, но не устанавливает, что обнаружение корректного действия не создаёт полномочие выполнить его. Реальная ошибка #342→#361 показала именно разрыв между выводом и разрешением на внешнее изменение.

Оставить как самостоятельный универсальный смысл.

### C02 — полномочие на решение ≠ знание/исполнение — PASS, но с узкой областью

C01 регулирует **разрешение на действие**. C02 регулирует **право сделать выбор/принять решение**. Это не одно и то же.

Пример: reviewer может иметь право проверить и рекомендовать, но не владеть продуктовым выбором.

Оставить как отдельный универсальный смысл; project roles в A остаются конкретизацией.

### C03 — масштаб вывода ≤ масштаб доказательства — PASS

Это самостоятельная компактная защита, которая реально поглощает:
- неполный scope → полный PASS;
- единичный случай → общее правило;
- неполный поиск → категорический отрицательный вывод;
- неполный denominator → точный прогресс;
- partial check → whole-system claim.

Оставить.

### C05 — не усиливать модальность — PASS

Hidden-premise guard U07 теоретически может поймать ошибку, но не делает различие модальностей достаточно явным. Реальные ошибки уже включали превращение наблюдаемого состояния/обычного пути в обязательное требование.

Оставить отдельным коротким правилом.

### C06 — условие остановки анализа — PASS

Текущий чат дал прямое подтверждение необходимости: анализ продолжался после того, как новые стресс-тесты перестали существенно менять архитектуру.

U10 о лишних вопросах это не покрывает. A-D3 покрывает только техническую диагностику.

Оставить.

## 5. Повторная проверка кандидатов, ранее отброшенных

### C04 причинность — NO-NEW-RULE подтверждено

Для универсального слоя достаточно U07 (скрытые посылки) + project A-D для технической причинной диагностики. Отдельная строка сейчас не даёт достаточного дополнительного выигрыша.

### C07 ложная точность / denominator / double count — NO-NEW-RULE подтверждено

C03 является достаточным общим принципом. Точный процент или точный остаток из неполного набора — прямое превышение масштаба доказательства.

### C08 baseline compatibility — NO-NEW-RULE подтверждено

C03 + A-F1/A-REV3 обеспечивают общий и технический уровни.

### C09 classification / false dichotomy — NO-NEW-RULE подтверждено

Это hidden premise / unsupported exhaustiveness. U07 достаточен; A-REV5 задаёт project-specific classification.

### C10 единичный случай → общее правило — NO-NEW-RULE подтверждено

Прямо покрывается C03.

### C11 применимость источника к объекту/версии/состоянию — предыдущее NO-NEW-RULE отменено

Результат: **ADD to U**.

Причина: истинность источника и достаточность доказательства не гарантируют применимость этого источника к текущей сущности.

Это отдельная ошибка, уже подтверждённая в `AGENT_LOGIC_ERRORS.md` на #362:
документация fine-grained tokens была применена как доказательство поведения другого token context.

C03 не полностью закрывает эту ошибку: доказательство может быть сильным и полным для **другого** объекта.

Нужен отдельный короткий смысл: применять факт/правило только к тому объекту, версии, состоянию и области, для которых источник действительно применим.

### C12 разовое исключение → общее разрешение — NO-NEW-RULE подтверждено

Покрывается C01: permission не расширяется за установленную границу.

### C13 новая инструкция того же уровня — NO-NEW-RULE подтверждено

Не следует создавать пользовательскую мета-иерархию поверх системной модели приоритетов без реальной необходимости.

### C14 прямое поручение не подменять типовым процессом — NO-NEW-RULE подтверждено

U10 + P01 достаточны; для project-specific конфликтов приоритет прямого указания уже установлен.

### C15 порог вопроса пользователю — NO-NEW-RULE подтверждено

U09 + U10 + C06 образуют достаточный маршрут: самостоятельно проверить → не тормозить при достаточных данных → спросить только когда задача реально не определена/нужен выбор.

### C16 shared evidence / multiple agents — NO-NEW-RULE в U подтверждено

Для Vico есть явное A-REV5: совпадение нескольких агентов само по себе не подтверждает finding. Универсальная часть поглощается U07/C03.

### C17 отсутствие подтверждения / отсутствие найденного объекта — NO-NEW-RULE подтверждено

Это частный случай C03 при корректном применении: область отрицательного вывода не может быть шире проведённого поиска/доказательства.

## 6. Проверка project-specific PR permission gap

Подтверждено: текущий A-R3 запрещает Мире **менять назначенный служебный PR** без прямой команды, но не задаёт общего правила «не создавать новый PR любого типа без прямого разрешения разработчика».

Это реальный project-level gap, подтверждённый произошедшей ошибкой.

Размещение: **A**, не U.

Важно: C01 не заменяет точный project permission contract. Универсальный принцип помогает рассуждать правильно, но repository workflow должен явно определять, какие GitHub-действия разрешены.

## 7. Конфликты между слоями

### U09 vs A-P3 «смотри шире непосредственного поручения»

Конфликт потенциальный, но разрешимый:
- U09 требует держать исходную цель;
- A-P3 требует замечать существенные соседние проблемы;
- A-REV5/A-G3 ограничивают расширение текущей реализации.

Следствие: «заметить» не означает «самостоятельно исправить». C01 делает эту границу явной и снимает конфликт.

### U10 «однозначно → выполнять» vs project permissions

Конфликта нет при условии C01: однозначность задачи не создаёт отсутствующее разрешение на внешнее действие.

### C06 «остановить анализ» vs A-D техническая диагностика

Конфликта нет: C06 останавливает анализ только после достаточности данных; A-D конкретизирует, что считается достаточностью для технической проблемы.

### U04 external-current info vs A-G5 official docs

Не конфликт, а audience specialization: U действует для ChatGPT вообще; A-G5 гарантирует тот же проектный минимум для всех repository-агентов.

### Новые универсальные смыслы, которые действительно прошли проверку
1. C01 — finding/fix не создаёт permission; разрешение ограничено scope.
2. C02 — право решения отдельно от знания/исполнения/способности.
3. C03 — масштаб вывода не превышает масштаб доказательства.
4. C05 — не усиливать модальность утверждения.
5. C06 — прекращать анализ при достаточности данных.
6. C11 — проверять применимость источника к конкретному объекту/версии/состоянию.

Итого после loss-check: **шесть**, а не пять новых универсальных смыслов.

### Project-specific изменение, требующее отдельного решения разработчика
- точный A-level запрет на создание любого нового PR без прямого разрешения разработчика, вместе с уже существующим запретом смены назначенного служебного PR.
