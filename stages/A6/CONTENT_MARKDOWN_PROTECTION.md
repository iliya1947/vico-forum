## LENA-TRANSLATION-TOKEN-RESTORE-01 — P3 — current foundation defect

Protected technical fragments are restored using a JavaScript replacement string rather than literal substitution.

- content-markdown-translation.ts:61–72,390–422,443–485 captures technical fragments, including paths containing dollar and ampersand, and substitutes ordered unique protected markers in semantic text. :333–349 validates the complete expected marker sequence, then executes restored.replace(token.marker, token.value). JS interprets dollar replacement sequences within token.value; these are not literal replacement text.
- Concrete plain Markdown source: "Use /tmp/$& now." Path regex captures the exact fragment /tmp/$&. A correct identity provider response keeps the generated marker intact. Isolated JS evaluation of the actual regex and replacement expression with marker ⟦VICOPROTECTED0X0X0⟧ returned "Use /tmp/⟦VICOPROTECTED0X0X0⟧ now." rather than the original path. This was an isolated language-semantics check, not a project test or provider call. Other substitution sequences can also corrupt technical fragments where accepted by the patterns.
- The sequence check happens before replacement. Restored tree serialization/reparse :204 and structureSignature :540–560 intentionally ignore the value of translated text nodes. This replacement leaves the plain-text node structure unchanged; no post-restore marker or literal technical-value check catches it. content-post-body-publication.ts:82–96 sends restored content to publication store. DB content-post-body-execution-store.ts:211–226 passes that text to trust-bound revision store; ordinary read validation checks identity/provenance and quote attribution, not this path's literal value. Thus current implementation can accept a corrupted translation despite an otherwise correct provider response. Full integration execution not performed.
- CNT-04 explicitly requires preserving URLs/technical fragments; PROJECT_STATE:109 records protected user-content translation foundation as implemented. This is a defect in the existing implemented algorithm, not a request to activate future providers. No real provider, deployed publication or security exploit claimed. P3 because technical text corruption is established in the prepared current foundation, not a runtime exposure claim.
- Existing repeated URL/identifier tests (:199 onward) preserve ordinary fragments but do not cover replacement-string metacharacters. Corrective expectation: restore exact literal protected values and reject corruption; regression with path containing dollar/ampersand and multiple protected tokens, identity and translated prose, through restore and publication. No new architecture required.
