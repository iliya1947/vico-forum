## LENA-TRANSLATION-ALLOWANCE-BYPASS-01 — P2 — current implemented foundation

A terminal-only allowance admission is persisted as actual provider authority, so a later supported execution can make a provider call without an actual allowance decision.

- content-provider-allowance.ts:165,191,240,270,281,407–426. For a configured provider that cannot support the source/capability, both title/body gates call persistTerminalUnsupportedAdmission; for an out-of-bounds body the gate also calls persistContentProviderAllowanceAdmission directly. Neither path calls allowance adapter.admit. This is intentional solely to enter the existing claim/failure lifecycle without provider work. Ordinary successful admission uses the same persistence method (:383). Both return the same outcome admitted/provider. A real admitted decision may omit reservationReference, so null reference cannot distinguish these cases.
- db/translation-task-store.ts:193–207 reuses admitted state for exact generation/attempt without a new allowance check. :268–325 persists identical state and provider for both paths. :1009–1036 claim checks admitted generation/attempt and clears allowance columns; it does not distinguish terminal-only authorization. Migration 0019 has no terminal-only discriminator. Both executors then obtain provider ID from gate result and re-evaluate actual capability before raw provider call. Title executor :90,116–121; body executor :111,151–170. Capability recheck is not provider allowance admission.
- Concrete supported scenario: title planned while allowed, capability/data policy subsequently denies its pair. Gate persists terminal-only admitted state for the configured provider, without actual allowance. Execution interrupted before claim (ordinary durable recovery window). Same task generation and attempt remain pending. Capability becomes supported again; provider ID, source/revision, target, generation policy unchanged. New gate returns admitted from persisted state without adapter invocation, consumer passes current source preflight, claim succeeds, router actual support now passes, adapter translates. The allowance adapter may even be absent or currently defer. Alternatively capability changes between gate and claim within one process: existing data-policy interface allows reevaluation, and cloudflare-m2m100-provider.test.ts:184 explicitly exercises mutable policy revocation. A configuration/dependency change that affects admission but not required translated output does not necessarily change generation policy version. No assumed second provider or new external integration required to establish the algorithmic counterexample. Analogous body bounds change may create same issue; same root, count once.
- Current source-of-truth JOB-03/SEC-02 and CNT-01 require bounded provider execution and deduplication, while current allowance implementation explicitly asserts terminal-only bypass can never cause provider work. #315 J4/J5 concluded actual allowance before raw egress; this counterexample establishes a missing distinction in existing foundation. Actual Worker generation/provider/allowance configuration remains disabled/deferred Stage6; no observed spending or live abuse. P2 is potential financial/resource effect of the already implemented admission/recovery algorithm, not a claim of deployed vulnerability. No project runtime reproduction performed.
- Existing content-provider-allowance.test.ts:334–383 explicitly asserts the synthetic admitted outcome and no adapter call for unsupported title; analogous body test :465 onward. Current executor tests terminalize unsupported pair under unchanged capability; they do not prove the durable interrupted terminal-only admission remains non-executable when capability changes. Corrective expectation: no provider call unless corresponding real allowance authorized the actual execution occurrence/provider/envelope; terminalization-only authority cannot be reused for provider work, including across interruption and capability changes. Regression with same durable task, denied support at gate, later supported at execution and allowance unavailable/denied; retain terminal handling when unsupported and correct real admission.
