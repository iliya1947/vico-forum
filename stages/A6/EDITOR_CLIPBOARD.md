## LENA-EDITOR-HTML-LITERAL-01 — P3 — current

Supported HTML prose text is escaped with a narrower function than literal plain paste, then interpreted as authored Markdown structure. Example: ordinary copied paragraph <p>Text {:vico-dir=rtl}</p>, with corresponding plain clipboard text and no tabs.

1. clipboard-markdown.ts:98 converts text nodes with escapeText (:8), which does not escape direction markers, line-leading ordered markers, pipe or spoiler syntax. In the example, resulting source is exactly Text {:vico-dir=rtl}; normalizeClipboardProse trims wrapper spacing only; valid remains true.
2. visual-markdown-editor.tsx:585–615 handles normal rich paste (not Ctrl+Shift+V), invokes clipboardHtmlToMarkdown and directly calls onReplaceRange with converted source. No warning, fallback or subsequent escaping for a non-null result. markdown-editor.tsx:517–535 records and sets that Markdown source, hidden form field :1141 serializes it.
3. In a full selected paragraph replaced by this fragment, markdown-syntax.ts applyParagraphDirections recognizes the terminal marker and removes it from the visible text while setting direction. User copied literal visible characters, not an explicit direction operation. Renderer/preview share this semantic behavior. A literal HTML paragraph starting with valid Markdown list/heading syntax also may become unintended structure. No active HTML/XSS path claimed.
4. EDITOR.md §10 requires preserving supported structure and safe fallback rather than silent data loss; §2 requires semantic/content preservation. Plain path already protects Vico direction/spoiler/table syntax, so the gap is in HTML text-node conversion, not renderer or intended direction syntax. Test suite verifies plain marker escaping and actual formatted HTML but lacks this rich-literal regression. Expected regression: normal HTML+plain paste replaces selected prose with literal marker text, unchanged intended direction and no newly invented structure; actual HTML headings/links/formatting remain supported. No duplicate of A6.1a terminal-pipe defect or #315 E2 renderer finding.

## LENA-EDITOR-PASTE-CODE-TAB-01 — P3 — current

Ordinary rich paste of tab-indented source code can be incorrectly converted into a spreadsheet table, bypassing the supported preformatted code conversion.

1. Repro input: text/html = <pre>\tfoo()\n\tbar()</pre>, text/plain = "\tfoo()\n\tbar()" (actual tab/newline characters), selected existing prose leaf. This is a supported preformatted clipboard representation; no unsupported HTML required.
2. visual-markdown-editor.tsx:603–606 checks plain.includes("\t") before HTML handling, unconditionally invokes onPasteTable and returns. clipboardHtmlToMarkdown's pre branch :113–117, which generates a safe fenced code block preserving code contents, is never reached.
3. markdown-editor.tsx:543–550 calls spreadsheetToMarkdown. technical-markdown.ts spreadsheetToMarkdown accepts rectangular 2-column rows including empty cells; the first row becomes headers, second row data; encodeTableCell escapes punctuation. Result is a table of empty first column, foo() header and bar() row, not source code; no fallback warning because conversion succeeds. Normal paste updates shared authoritative Markdown and can subsequently be published.
4. EDITOR.md §10 specifically requires preserving IDE/GitHub code indentation and newlines, and tables only where appropriate. This is independent of literal HTML escaping; even a correct HTML converter is bypassed. Existing component tests :1640–1680 verify actual TSV; :2445–2471 verifies tab-indented code only via forced Ctrl+Shift+V (which takes an earlier branch). Expected regression: rich preformatted clipboard with tab-indented rectangular text preserves code; actual rectangular spreadsheet clipboard still yields table. Plain-only ambiguous source vs TSV may need explicit classification, not inferred as a separate proven defect. No browser execution.
