# User AI / Vico Consultant — технический план

**Статус — готов к проверке Business-Мирой.** Продуктовый контракт задан D-25–D-32. Техническая база проверена по `main` `99b40480cb4d777298aafb1ffae7f28cf0c6085d`. Поиск и Help уже имеют свои canonical readers, контент хранится в immutable revisions, видимость определяется текущим состоянием темы и сообщения. Индекс Consultant будет производной поисковой проекцией. ## 1. Архитектура и путь запроса

| Слой | Ответственность |
| --- | --- |
| Forum UI | Один launcher и panel на уровне постоянного локализованного layout. Тот же panel открывают Search, обычная тема, Help и Editor. Гость видит вход и существующие Sign in/Register links. |
| Consultant API | Явный same-origin POST из panel. Существующие Better Auth, active account, LocaleRegistry и разрешения. Закрытый DTO запроса, страниц и результатов. После длительного provider call, до отправки ответа, повторно проверить сессию, disclosure и актуальность evidence. |
| Consultant core | Распознаёт ограниченный набор намерений. Разделяет discovery, правила и навигацию, Help, размещение вопроса и краткое объяснение уже доступной темы. Компонует проверенные ссылки и ответы из допустимых источников. |
| Общий retrieval | Lexical search, похожие Help-вопросы и semantic candidates используют один Forum reader, одну публичную политику и одну проекцию. Search получает расширенную выдачу, Consultant — до трёх карточек, Help сохраняет существующий вход в проверку похожих вопросов. |
| PostgreSQL | Источник текущего состояния форума, производная pgvector-проекция и короткие записи допусков, статуса индекса и квот. |
| Workers AI | Один адаптер эмбеддингов и один адаптер генерации короткого ответа. Оба получают строго отобранные данные. Они не получают инструменты, URL для вызова, доступ к хранилищу или право записи. |

Реализовать request-local `ConsultantDependencies` в существующем Worker и новый ресурсный маршрут рядом с `app/routes.ts`. Использовать `authSessionForRequest`, локализованный route context и текущий PostgreSQL web runtime. На сервере получать actor из сессии, применять same-origin и POST, проверять привязку к активному аккаунту перед выдачей допуска или чтением/отправкой контекста. Гость, непригодная сессия, off switch и невалидный DTO не расходуют AI allowance. Ответы и ошибки — `private, no-store`. Публичная загрузка страницы сохраняет обычное поведение при отсутствии provider.

Вход содержит случайные `consultationId/turnId`, ограниченный текст вопроса, типизированный page context и ограниченные IDs/выбранные значения для продолжения. Контекст передаётся как discriminated union: search term, topic/post ID, category/section ID или editor placement hint. Произвольный URL, actor, disclosure layer и полный DOM не принимаются. Идентификатор из клиента всегда подсказка. Сервер сам восстанавливает текущий допустимый контекст. Передать только выбранные данные и короткую историю намерения; provider получает текущий вопрос и подтверждённые источники, а не полный клиентский transcript.

| Запрос | Результат |
| --- | --- |
| Найти обсуждение или решение | Общая выдача ранжирует найденные темы. Consultant показывает до трёх с короткой проверяемой причиной, solved/best-answer только из текущей проекции. Явно лучший результат отмечается при подтверждённом отрыве. Для длинной выдачи используется стандартный Search. |
| Куда задать вопрос | Canonical structure и Help capability дают section/category и тип темы. Подсказки tags берутся из текущей таксономии; title — короткое предложение, редактируемое пользователем. При недостатке информации — один вопрос о цели или технологии. При отсутствии хорошего совпадения явно сообщить это и дать доступный путь создания. |
| Как найти функцию | Статический каталог текущих forum operations и server-side route builders дают шаги и ссылки. Входы Watch/Bookmarks/Mute/Block, профиль, язык/Settings, уведомления, best answer, жалоба и Help используют существующие пути и guards. |
| О чём тема | Передать только разрешённые выдержки из current title, исходного вопроса и полезных видимых ответов. Краткий ответ с привязкой к исходным постам. При бедном контексте указать, что удалось установить. Отдельного summary режима, истории или регенерации нет. |

LLM может предложить intent и короткий текст на известных фактах. Ответ проходит закрытую schema, bounded plaintext и проверку возвращённых evidence ID по набору этого вызова. Достоверные действия, ссылки, роли, метки solved/best answer и наличие материалов строит сервер. Для advice использует канонические объяснения. Модель не диагностирует форумные нарушения, не создаёт пост, не меняет настройки, не вызывает инструменты. Неизвестный/невалидный вывод даёт локальный ответ или обычную ссылку Search/Help.

## 2. Полномочия, knowledge и границы данных

`main` уже разрешает capabilities через `authorizationForRequest(context).forUser(session.user.id)`. `adminAccess.canEnter` включает часть forum permissions и подходит для допуска в Admin shell. Для назначения слоя Administrator этот общий флаг слишком широк. Использовать точечные effective permissions из одного актуального resolver snapshot, включая реальные grants/overrides, Owner projection и действующие ограничения по канонической политике.

| Слой | Правило выбора | Разрешённый контекст |
| --- | --- | --- |
| User | Активная сессия и отсутствие признака старшего слоя | Публичные материалы и пользовательские описания возможностей, настройки и собственные страницы как navigation cards. |
| Moderator | Есть хотя бы один реальный moderation anchor из нативных Attention/visibility gates: например, `forum.content.visibility.manage`, `forum.solution.manageAny`, `forum.helpDuplicate.manage`, `forum.helpNeedsDetails.manage`, `forum.complaint.review`, `forum.complaint.appeal.review` или `forum.attachmentSecurity.read` | User и точечно разрешённые инструкции навигации по существующим модераторским страницам. |
| Administrator | Есть административный anchor из канонических gates: `access.authorization.manage`, `admin.history.read`, `admin.users.read`, `admin.users.blocks.manage` или `forum.structure.manage`. Для owner-only ссылки дополнительная проверка exact Owner | User, Moderator и точечно разрешённые административные страницы/справка. Administrator не даёт разрешение на все Moderator cards. |

Названия ролей, UI claims, prompt и признаки общей видимости страницы не выбирают слой. Каждый knowledge entry несёт минимальный слой и реальный permission/предикат страницы либо ресурса. При выборе Moderator разрешён только проход соответствующего guard. Для settings/account и contextual action требуется текущая нативная применимость. Владелец форума определяется существующей серверной привязкой. Wording о маршрутах не раскрывает denied entry через автокомплит, список возможных tools, цитату или отрицание. Если permission snapshot недоступен, закрыть protected output и inferencing для этого запроса, вернуть обычные публичные ссылки только из известного публичного каталога. Токены/выбранные права другому пользователю не переиспользуются. [Авторизация](../../docs/auth/AUTHORIZATION.md) · [Admin access](../../docs/ADMIN_PANEL.md)

Knowledge entries — маленькие versioned локализованные записи по реальным страницам. В коде хранить stable route/feature key, layer и предикат. Человеческие строки идут через существующие локализационные ресурсы. Повторно использовать `app/forum/paths.ts` и canonical route helpers, валидировать locale через `LocaleRegistry`. При смене route test catalog обнаруживает выбывшую ссылку. Выбор места для новой темы переиспользует существующий ordinary category/section tree, статику Help и актуальные permission/AP-10 hints. Он не использует скрытые разделы и не обещает публикацию при denied.

| Данные | Обработка |
| --- | --- |
| Текущие открытые title/body/tags, видимый best answer | Bounded public projection может идти в embeddings или короткий ответ. Секреты и чувствительные куски исключаются фильтром допуска. Непригодный фрагмент остаётся доступным по своим форумным правилам. |
| Текст запроса | Пользователь передаёт явно. Для внешнего вызова — короткая необходимая часть. При обнаружении ключей, токенов, credential URL или персональных полей использовать локальный режим. Детектор снижает риск, абсолютную полноту не обещает. В панели кратко указать, что для AI ответа может обрабатываться отправленный текст. |
| Черновик Editor | Без отправки текущего body, вложений, raw DOM или выделения на каждое изменение. Placement hints — текущий section/Help, существующие tag IDs и текст, который пользователь сам отправил. Возможные title/tags — предложения, вводятся только действием пользователя через обычные контролы. |
| Private профиль, account/session, History, Complaints, hidden revisions, staff queues, attachments | Никаких raw records, excerpts, секретов и приватных ID внутри общего индекса или provider context. Привилегированная навигация строится локально из разрешённых карточек, без отправки внутренних данных provider. |
| Недоверенные forum posts, user turns и model text | Размечаются как данные, проходят длину/формат, не интерпретируются как tool instruction. Link и action — enum + серверная сборка. Ответ рендерится безопасно, без HTML, fetch markup или URL модели. |

Перед отправкой public context проверить актуальную видимость/ревизию, при ответе заново гидратировать ссылки и зависимости. Если использованный источник спрятан, причину либо summary, построенные на нём, удалить целиком или заменить локальным доступным ответом. Проверка применяется к новой передаче provider и к выдаче нового ответа. Уже просмотренный пользователем текст нельзя отозвать. На следующем turn/навигации не переносить ранее раскрытые privileged facts после смены прав и не отправлять прежний свободный текст ответа обратно модели. Логи/analytics, error payloads и caches не содержат transcript, поисковый текст, body, provider payload или credentials.

## 3. Память консультации и UX

- Состояние v1 — in-memory store вкладки в постоянном локализованном layout, интерфейс `start/get/append/end/reset`. Содержит bounded turns, draft диалога и источники/intent, UI не хранит секрет сессии. Сохраняется в client-side навигации по Search, topic, Help, Editor, настройкам и смене локали, если не меняется actor. Для перехода locale не создавать второй store, панель монтируется в общем shell. F5, закрытие вкладки и новая вкладка начинают отдельную консультацию. Нет localStorage, cookie transcript, серверных диалогов и долговременной памяти.
- Свернуть панель — сохранить текущую консультацию. «Завершить» — очистить turns/context, отменить in-flight, удалить ссылку на результат и сменить generation. Выход, смена учётной записи, session-revoked response очищают всё. Поздние ответы принимаются только для совпадающих consultation/turn/generation и активного actor. Permission downgrade очищает защищённые cards, следующий ресурсный запрос заново считает слой. Replaceable store позволяет позднее добавить серверную persistence, не меняя retrieval и ответы.
- Launcher визуально внизу справа с safe-area и отступом от overlay, соответствует D-30 и в LTR, и в RTL. Не перекрывает composer, навигационные кнопки и системный popover. У панели один заголовок и понятные действия отправки, закрытия, завершения. Контекстные кнопки используют существующие места выдачи и label «Консультант». Они не отправляют просмотр или draft автоматически.
- Desktop — немодальная панель с корректными landmarks, управлением focus и возможностью продолжить работу. На малых экранах допустим modal sheet с focus trap и возвратом фокуса. Escape закрывает, мобильная клавиатура и 200% zoom оставляют input/Send видимыми. Pending/result/error объявляются через live region. RTL устанавливается через текущий layout, для исходных цитат и технических строк применяются `dir=auto` и bidi isolation, code показывается текстом.
- Интерфейс локализован через текущий common catalog и active locale registry. Вопрос на другом языке не переключает UI locale. Обычный ответ следует текущей локали или явно указанному языку, RU/HE/EN — проверяемые примеры. Исходные имена, имена API, сообщения об ошибках и идентификаторы в коде остаются точными. `und` не превращается в искусственно угаданный источник.
- Guest launcher доступен с клавиатуры и открывает auth-gate с существующими Sign in/Register routes и безопасным способом вернуться на текущую страницу. Никаких вызовов inference до входа. При недоступном AI панель предлагает canonical Search/Help и настройки согласно запросу, Editor и навигация сохраняют свои входы. ## 4. Общий поиск и текущий индекс

1. **Лексическая база.** `app/routes/search.tsx` вызывает `ForumReader.search`. `db/forum-repository.ts` уже сопоставляет current title, tags и current visible post bodies, ранжирует title → tag → body и не возвращает hidden topics. Help использует независимый существующий bounded reader `searchHelpSolutionsSimilar` и свой lexical rank. На этом основании добавить общий orchestration service retrieval с режимом whole forum / Help. Оба lexical reader сохраняют результат и fallback. Для bounded rerank допускаются несколько поисковых терминов из актуального вопроса с общей DB deadline. Формирование term/query, экранирование и canonical public projection остаются в существующих слоях. Пустой/слишком длинный ввод обрабатывается текущими правилами.
2. **Семантические кандидаты.** Индекс по одной записи на публичную тему. Вход embedding — current title, нормализованные tags, ограниченные репрезентативные фрагменты вопроса, других видимых ответов и best answer. При длинных темах сначала включать вопрос и best answer, затем короткую детерминированную выборку остальных public сообщений. Сохраняются язык источника и технические идентификаторы. `isSolved`, статус best answer, section/category и доступность ссылок читаются заново из канонической темы. Категория и названия разделов участвуют в ранжировании и маршрутизации через текущую структуру, поэтому их переименование не требует массового пересчёта векторов. Search продолжает находить все текущие видимые сообщения lexical-путём.
3. **Projection и поиск.** Хранить `vector(256)` в той же PostgreSQL web-БД треком `modelId + dimensions + sourceVersion + projectionVersion`. На запуске измерить exact cosine search при ограниченном corpus/statement deadline, при недостаточной производительности добавить HNSW cosine по измеренному плану запросов. Выдавать ограниченные candidate IDs. Гидратация батчем через узкую публичную проекцию существующего Forum repository, по тем же joins, guards и revision semantics. Generation кандидата и его current revision set проверяются в одном snapshot, перед ответом источник подтверждается заново. `readTopicPage` загружает весь тред и вложения, поэтому для кандидатов/LLM нужен bounded reader по выбранным ID, переиспользующий public visibility и current-revision selection. Сохранять native localized links, закрытые треды, unsolved, hidden post stubs и прочие текущие правила. Векторы, отсечённые кандидаты и внутренний score не выходят из сервера. [pgvector на Neon](https://neon.com/docs/extensions/pgvector) · [Hyperdrive](../../docs/database/HYPERDRIVE.md)
4. **Выдача.** Объединять lexical и semantic candidates по canonical topic ID с reciprocal-rank fusion и детерминированным tie-break. Точное заглавие, tag или error token получают приоритет. `solved` и видимый best answer — небольшой бонус после проверки релевантности. Они не вытесняют значительно более подходящую unresolved тему. Отдельный минимум качества для semantic-only калибровать на русском, иврите, английском и смешанном корпусе. В слабой выдаче не добирать три. Для карточки сервер строит причину из проверенного совпадения title, темы, тега, видимого excerpt или релевантного фрагмента и помечает, установлен ли solved. Любые объяснения LLM ссылаются только на те же evidence IDs. Широкую Search-выдачу выдавать в текущих пределах. В Help сохранять его узкий corpus и доступный check-similar даже при отключении Consultant.
5. **Поверхности.** Lexical Search и first paint работают независимо от Workers AI. Для signed-in поиска — прогрессивный hybrid POST с тем же q после завершённого поискового submit. При отсутствии сессии Search остаётся lexical-only. Для Help добавлять semantic к явному существующему similarity submit через тот же service лишь в пределах его guard и deadline. При timeout/No quota вернуть тот же уже доступный lexical result. В SSR loader, на keypress, открытии panel и контекстной навигации provider не вызывается. На новых тексте, query, locale или account отменять устаревший запрос либо отбрасывать ответ. В Consultant можно использовать тот же текущий shortlist и bounded summary без повторного эмбеддинга той же заявки.
6. **Lifecycle.** В той же канонической транзакции, которая публикует или меняет текущий title/post, source-locale revision, tags, best answer или visibility, обновлять per-topic generation узкой функцией после штатных доменных проверок. Ordinary/admin/Help paths сводятся к этой функции. Изменение, которое не меняет embedding, читается runtime из текущей структуры/метаданных. При Hide темы сразу сделать её vector непригодным, при Hide отобранного поста invalidate весь документ. При Restore тема/пост видны lexical-путём сразу, embedding позже. Semantic reader использует запись только при `indexedGeneration = sourceGeneration`. Запаздывающий index worker не меняет это правило. Изменение закрытого треда, если оно не затрагивает документ, не перерасходует inference. Hard-delete, если допустим существующим lifecycle/миграцией, каскадно удаляет производный документ.
7. **Индексация.** Одна durable запись на topic с dirty/generation, lease, attempts и next eligibility, без копий текста. Ограниченный scheduled Worker drain использует существующие PG deadline/lease conventions. `FOR UPDATE SKIP LOCKED` резервирует малую порцию. Перед вызовом заново получить допустимые public sources/revisions, нормализовать и проверить admission. Вызов провайдера без открытой DB transaction. После ответа проверить claim, актуальные revisions, eligibility и generation в короткой транзакции, затем CAS upsert. Read-side SQL/гидратация повторно фильтруют stale/hidden даже при запаздывающем drain. Повтор одинакового source digest/model reuse без вызова. При смене модели не смешивать vector spaces. Прежний generation удаляется или размечается непригодным, пока идёт bounded rebuild. [Жизненный цикл translation jobs как образец](../../docs/translation/PROVIDERS_AND_JOBS.md)
8. **Backfill и cleanup.** Идемпотентный keyset по существующим публичным темам с cursor, ограниченным числом SQL строк и с учётом одновременных записей из канонических writers. Backfill добавляет missing work, не перезаписывает новый epoch. Устаревшие embeddings удаляются при invalidation либо ограниченным cleanup, который не задерживает запрет чтения. Retry только для retryable ошибок с backoff и пределом; stale становится новой generation, invalid policy — terminal для неё. Планировщик обслуживает только derived search index. Частный transcript и background summary в него не попадают. До разрешённого внешнего rollout binding/cron выключены, существующие writers работают и при пустом индексе.

## 5. Провайдер, лимиты, данные и эксплуатация

**Выбор для первого подключения — Workers AI в существующем Cloudflare аккаунте.** Embedding — `@cf/google/embeddinggemma-2`, 256 измерений, официальные text retrieval prefixes. Generation — `@cf/google/gemma-4-26b-a4b-it` с малым `max_tokens` и structured output там, где адаптер подтверждает формат. Ограничить контекст источниками и выбранной локалью. Прямая Workers AI binding с фиксированными model keys, без платного fallback, AI Gateway logging, файлообмена и внешних URL. В локальном CI это dependency-injected adapters с детерминированными fixtures. У провайдера документированы multilingual/code embeddings и zero data retention для обычных stateless запросов с оговорёнными исключениями. Практическое качество RU/HE/EN и правила обработки именно на используемом аккаунте принадлежат Stage 6. [EmbeddingGemma 2](https://developers.cloudflare.com/workers-ai/models/embeddinggemma-2/) · [Gemma 4](https://developers.cloudflare.com/workers-ai/models/gemma-4-26b-a4b-it/) · [Политика обработки](https://developers.cloudflare.com/workers-ai/platform/data-usage/)

| Операция | Ограничения |
| --- | --- |
| Navigation/feature | Сначала локальный каталог. Генерация для однозначного известного маршрута не нужна. |
| Topic discovery | Один admitted query embedding на turn или поиск. Повтор одинакового текущего запроса того же пользователя дедуплицируется в коротком окне. Не сохранять private queries, vectors или cross-account query cache. |
| Summary/короткое пояснение | Не более одного generation call на turn, только если есть разрешённые evidence. Bounded вход и выход. Timeout и validation failure дают локальную навигацию, extractive reason или отказ от вывода. |
| Indexing | Только публичный контекст. Content/model/version fingerprint и bounded leases. Cron ждёт свободного бюджета, а основной форум и lexical остаются готовы. |

Входные ориентиры для расчёта — до 1 200 input tokens и 240 output tokens на generation, до 256 input tokens для query embedding и 1 000 для документа. После замера overruns лимиты могут снижаться. Резервировать по доказанной верхней границе token use, включая model framing. До согласования токенизации использовать безопасную верхнюю границу UTF-8 и известного overhead, а при неопределимой верхней границе не вызывать provider. При официальных 9 091 input и 27 273 output neurons/M generation при 1 200+240 стоит около 17,5 neurons. Query/doc embedding при 154/M стоят около 0,04/0,15 neurons. Это оценка размера, а не доступный daily трафик. В Free Workers выделено 10 000 neurons в день на аккаунт, reset 00:00 UTC. Расход иных Workers и фактический остаток ещё нужно сверить. [Тарифы моделей и общий лимит](https://developers.cloudflare.com/workers-ai/platform/pricing/)

1. **Один hard admission перед каждым провайдером.** Использовать паттерн PostgreSQL reservation и occurrence identity из текущих translation admission contracts. Переиспользовать `db/content-request-budget-store.ts` / `app/localization/content-provider-allowance.ts` на уровне общего механизма, если они сохраняют разные unit/time-window/domain contracts. Сами translation capabilities/коды контента не расширять AI задачами. Если потребуются отдельные таблицы учёта по units, один общий account-level coordinator считает translation reserve и AI budget перед внешними calls. Раздельные независимые счётчики, которые могут одновременно израсходовать один Free остаток, не подходят.
2. **Приоритет обязательных переводов.** Выделить заранее согласованный reserve для translation до допуска любой операции User AI. Остаток под User AI дополнительно делится на интерактивную выдачу и низкоприоритетный backfill. Также ограничить per-active-account количество попыток, общий concurrency, ежедневные calls и CPU/SQL/хранение. Без согласованных чисел или без общей возможности enforce account budget AI provider остаётся выключенным. Переводы не получают дополнительного дефицита из-за включения User AI.
3. **Контроль нулевой стоимости.** Только подтверждённые Free plan и account-wide hard cutoff, действительный и для Workers AI. Если аккаунт Paid с overage либо доступный остаток не контролируется, binding для User AI не включать. Neon/Hyperdrive/Workers планы и остатки сверяются отдельно. Вектор 256 float32 — около 1 КиБ сырого payload на тему до таблиц/индекса/WAL. Измерить database growth и compute, держать ниже свободного места и лимитов с запасом форума. При достижении лимита новый backfill ждёт, stale rows очищаются, lexical сохраняется. [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) · [Hyperdrive Free](https://developers.cloudflare.com/hyperdrive/platform/pricing/) · [Neon Free](https://neon.com/docs/introduction/plans)
4. **Сбои.** Дедупликация по actor+consultation+turn+purpose либо topic+generation+model. Один in-flight turn на консультацию, коротко живущий marker для повтора. Не сохранять private query/output для replay. Повтор с тем же ID возвращает только безопасный маркер in-progress или completed. Browser может использовать уже полученный локальный результат. После потери результата нужен новый явный turn. Сумму reservation при неопределённом результате провайдера считать израсходованной. Автоматических paid retries и повторного вызова на пользовательском request нет. Локальные счётчики outcome/cache/admission/index lag без prompt и broad user IDs. Операционные traces только bounded IDs, модель/codes, время и расход.

## 6. База, rollout и fallback

Вперёд совместимые миграции добавляют vector extension, производную таблицу индекса с FK и учёт допусков. Журнал/снимок Drizzle, structural manifest, web runtime and migrator grants и disposable PostgreSQL 17 fixtures обновляются по действующей процедуре. Table/index schema не копирует исходный текст и не хранит дампы моделей. Extension устанавливает migrator, web role получает только нужные операции на точных relations. Никакой зависимости publish/edit/hide от доступности AI. Подключённая транзакция поддерживает только дешёвую и стабильную запись version/dirty. При Rollback UI/retrieval приложение может работать с прежней схемой. Если отключается новая запись dirty при сохранении v1-схемы, запуск semantic после повторного включения требует новой проверки source signatures или bounded reconcile. [Миграции](../../docs/database/MIGRATIONS.md) · [Hyperdrive и grants](../../docs/database/HYPERDRIVE.md)

Раздельные runtime флаги Consultant, hybrid retrieval и index drain позволяют оставить форум на canonical lexical. При аварийной деактивации сначала закрывается provider admission, затем hybrid/panel переходят в безопасный fallback. Index rows можно удалить или пересобрать отдельно от Forum data. В живом worker запросы rehydration/read-before-egress используют актуальный web binding без cache, который мог бы вернуть hidden или устаревший source. Таймаут retrieval/generation за пределами UX budget возвращает разрешённый partial result. Запросы записи/индексации не блокируют PG на время provider I/O.

Из runtime наблюдать отдельные счётчики health/coverage для index ready, stale, retry, backlog age, запросы и причины fallback, cumulative reserve и latency по классам. Для privacy-safe агрегатов использовать существующие observability patterns. Дефолтная конфигурация с выключенными provider, cron и deployed resources поднимается с пустым индексом. Сторонние app analytics, постоянный пользовательский log и дополнительный dashboard scope не нужны.

Ада собирает финальный head в первом PR, затем whole-feature review Business-Миры, независимая техническая проверка Лёвы на том же head и merge владельцем. ## 8. Repository/local-CI и quality acceptance

Использовать реальный built Worker и PostgreSQL 17 с миграциями, Better Auth и disposable fixtures, Chromium для связных потоков. Mock adapters заменяют inference, но не forum repository, auth, admission или revisions. Применимы `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm db:check`, `pnpm db:test`, build и connected browser acceptance. Требования к качеству проверяются на versioned cases с синтетическим форумным корпусом. Local workload тестирует алгоритм, выходной контракт и лимиты, фактическая языковая способность выбранной модели проверяется отдельно при допуске внешнего вызова.

| Покрытие | Проверка |
| --- | --- |
| D-25 и пользовательский scope | Детерминированные navigation flows, route/feature keys существуют. Discovery, solution, Help, section routing, language, bookmarks, report, settings, profile, notifications и placement ведут к фактической доступной странице. Общий программный вопрос даёт полезный следующий шаг на форуме. |

Deny у Moderator/Admin убирает соответствующую карточку, наследование не расширяет route permission. | D-27 и D-30, UX и память | Один panel живёт между Search/topic/Help/Editor, Settings и locale switch. Guest Sign in/Register подтверждён в EN/RU/HE. Close сохраняет текущую консультацию, Finish/logout/account change убирают данные и устаревший pending. Full reload/new tab начинают пустое состояние. Выдача не добирает слабые совпадения. Проверить Search с длинной выдачей и lexical baseline с отключённой семантикой. |

Ложный evidence ID, arbitrary URL, команда в title/body, смешанный bidi или token-like draft не порождают новых effects. При отсутствии источника нет выдуманного решения. Фактический вывод privileged navigation только из разрешённых entries. |
| Индекс и concurrency | Создание/Backfill, concurrent edit/hide/backfill, title/source locale revision, post visibility, best answer, restore, invalidated claim, два drain worker, stale response и модельная смена. Проверить ноль paid fallback и ноль provider calls на SSR/guest/off. При падении AI обычный Search, Editor, Help и navigation по-прежнему доступны. |

Для воспроизводимой языковой приёмки подготовить не менее 60 распределённых запросов RU/HE/EN. У каждого желательный topic или canonical route, ожидаемая допустимость, control lexical результат и признак «нет подходящего». Не менее 15 запросов проверяют cross-language, смешанный язык или code identifiers. Включить сильные exact matches, unsolved с лучшим ответным соответствием, distractors и stale/hidden. Предлагаемые стартовые gates для Stage 6 — **Recall@3 не ниже 85% на answerable subset**, 100% попаданий точного ID/имени в canonical маршруте, отсутствие деградации заранее отмеченных exact lexical hits и **ноль утечек/ложных ID**. Для каждого из RU/HE/EN отдельно измерить качество и разобрать systematic misses. Для summary вручную проверить, что все существенные утверждения опираются на допущенные evidence и code identifiers сохранены. Если gate не пройден, оставить соответствующий внешний AI путь выключенным и дать точную причину. Числа можно уточнить при review плана до запуска реализации, сравнивать по одному закреплённому корпусу.

## 9. Stage 6

Внешнее подключение требует отдельного разрешения владельца. Сначала сверить текущий Free план Cloudflare/Neon, общий остаток и переводный reserve, документированный режим stateless inference и запрет логирования body. Проверить vector extension/runtime ACL, worker timing при Free CPU и коротком provider SLA, нагрузку на WEB_HYPERDRIVE и объём индексируемого корпуса на разрешённых синтетических данных. Без доказанной стоимости и языкового качества флаги провайдера не включаются.

После разрешённого smoke сначала дать lexical+local navigation, затем небольшой backfill и hybrid, затем generation. На каждом шаге подтвердить актуальную видимость, измерить расход по классам и возможность instant downgrade до lexical. Binding, cron, DB grants, реальное embedding и generation, deployed smoke, аккаунтные квоты и любое переключение трафика лежат в указанном разрешении. Локальная приёмка не подтверждает производственное поведение.
