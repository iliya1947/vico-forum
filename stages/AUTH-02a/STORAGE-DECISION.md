**Заменить требование общего `rate_limit` для дополнительных Vico-бюджетов отдельной таблицей `auth_lifecycle_budget`.** Сохранить существующий `AuthLifecycleBudget` как единственный общий HTTP/direct admission service. Штатные Better Auth HTTP limits, `rate_limit`, schema mapping и configuration остаются прежними. Меняется storage существующего common budget; нового policy engine или native limiter implementation не требуется. ## Установленная причина и проверка альтернатив

1. [Better Auth 1.7.7 rate limiter](https://github.com/better-auth/better-auth/blob/v1.7.7/packages/better-auth/src/api/rate-limiter/index.ts#L133-L279): при успешном reset существующего native bucket вызывается `deleteExpiredRows`; `deleteMany` фильтрует всю модель только по `lastRequest < now - longestObservedWindow * 1000`. Предиката владения namespace или индивидуального срока у row нет. Longest window вычисляется из native/default/plugin/custom rules; direct service budgets в него не входят.
2. [Default context](https://github.com/better-auth/better-auth/blob/v1.7.7/packages/better-auth/src/context/create-context.ts): default 10 s; native special rules дают максимум 60 s. В #389 `betterAuthRateLimitOptions` содержит enabled/database/modelName без customRules; `vico-auth-lifecycle` не объявляет native rateLimit rules. Поэтому Vico 600 s окно не защищено от этого sweep. Простой возврат обычного last-request timestamp позволяет потерять действующий лимит.
3. [Официальный tagged storage contract](https://github.com/better-auth/better-auth/blob/v1.7.7/docs/content/docs/concepts/rate-limit.mdx): `lastRequest` — timestamp последнего запроса. Текущий #389 хранит там absolute deadline. Это объясняет, почему текущие тесты проходят, но подменяет семантику native поля. Namespace сам по себе проблему не устраняет.
4. Публичный `customStorage.consume(key, rule)` существует, однако заменяет storage всего native HTTP limiter. Для устранения локального конфликта это потребовало бы поддерживать ещё и native consume/expiry behavior. `secondary-storage` требует другой shared backend и затрагивает native behavior; in-memory непригоден для multi-worker enforcement. Native `modelName` переносит модель целиком. Ни один из этих путей не даёт namespace-safe очистку исходной таблицы при сохранении прежнего native implementation/configuration.
5. Dummy 600 s rule, перехват native DELETE по форме SQL/adapter predicate, private import, будущий timestamp и новое поле в native row без участия native cleanup не устраняют связность двух разных expiry contracts. Реальные native endpoint rules с другим window меняют enforcement и на foundation-ступени не обоснованы. Общую translation-таблицу также не переиспользовать: у неё translation-specific scope/subject/window/cost contract и другая web capability. `db/content-request-budget-store.ts` служит существующим примером явной expiry/locked bounded cleanup, без копирования translation service.

Локальная диагностическая проверка выполнена на реально установленном `better-auth@1.7.7`: вызван unmodified `onRequestRateLimit`, clock управляемый, adapter in-memory spy. При native `/get-session` reset на +120 s зафиксирован deleteMany только по lastRequest < now−60 s: Vico row с count=3 и truthful timestamp удалён до конца его 600 s окна; row с подменённым будущим timestamp пережил sweep. Дополнительно четвёртый `/sign-in/email` запрос получил 429 после трёх разрешённых. Никаких private imports в application не добавлено: доступ к dist использован только scratch-диагностикой. Это evidence native cleanup predicate, **не** PostgreSQL race test и **не** проверка ещё не написанного исправления. Runtime Node 24.19.0, pinned проектом 24.21.0; CI заново не запускался.

## Минимальный storage contract

1. `auth_lifecycle_budget`: `key text PRIMARY KEY`, `count integer NOT NULL CHECK (count > 0)`, `expires_at timestamptz NOT NULL` с finite-time CHECK. Key — прежний bounded versioned domain-separated HMAC (`vico-auth-budget:v1:` + SHA-256 digest); добавить CHECK формы/длины. Это единственная unique identity, отдельный `id` не нужен. Нет FK на user, plaintext email/IP/token, payload, native auth model mapping или новых identity/session records.
2. Btree `(expires_at, key)` для bounded expiry cleanup. Срок — реальный конец Vico fixed window от первого разрешённого consume (60/600 s по PLAN §7), полученный из authoritative DB clock. Внутри действующего окна успешный consume увеличивает count, сохраняя expires_at; denied не увеличивает count и не сдвигает срок. Истёкшее окно атомарно заменяется count=1 и новым expires_at. Новая credential/mail/domain mutation после expiry всё равно проходит собственные проверки.
3. Одно атомарное `INSERT ... ON CONFLICT (key) DO UPDATE ... WHERE` для consume, с проверкой expiry/count на фактически конфликтующей row; нет read-then-write admission. `RETURNING` доказывает разрешённое изменение. Denial/Retry-After читается из заблокированной тем же admission transaction row и DB clock; missing/malformed state не превращать в разрешение. Только consume решает admission; cleanup не является TTL-проверкой. [PostgreSQL 17 INSERT](https://www.postgresql.org/docs/17/sql-insert.html) / [Read Committed](https://www.postgresql.org/docs/17/transaction-iso.html).
4. Bounded opportunistic cleanup: не более 64 **истёкших** rows одной этой таблицы за admission, ordered `(expires_at,key)`, `FOR UPDATE SKIP LOCKED` и удаление только выбранных rows с сохранённой expiry-проверкой. Использовать тот же transaction owner/deadlines. Concurrent live renewal нельзя удалить. Нельзя выполнять Vico cleanup в `rate_limit` или глобальную очистку native storage. Отложенная физическая очистка не продлевает enforcement window; немедленное удаление всех expired rows без traffic не обещается. Новый cron/queue/background subsystem не требуется. [PostgreSQL 17 locking/skip locked](https://www.postgresql.org/docs/17/sql-select.html#SQL-FOR-UPDATE-SHARE).
5. Сохранить порядок server-owned policy buckets: network до выделения target, затем target/user по текущему intent. Consume admission коммитится **до** domain work; учтённые ранние buckets остаются учтёнными и при отказе последующего bucket/failed mutation. При storage/control failure domain work не выполняется; uncertain COMMIT не повторять автоматически. AuthLifecycleTransaction один, тот же request-local client; budget нельзя присоединять к уже начатой domain transaction и откатывать вместе с неудавшейся mutation. Server-owned bounded receipt исключает повторное списание одного nested logical operation.
6. HMAC policy/rotation, trusted ingress/unknown-network contract, численные лимиты и disabled challenge configuration не расширять. Общие budgets не включают native HTTP implementation и не заменяют его. В AUTH-02a новые public flows остаются закрытыми.

## Обязательное evidence исправления

1. Native PG17 concurrent first insert и consume одного key: точно max successes, остальные 429, без unique-ID errors/overspend; no double count HTTP/direct/nested service и failed-domain attempts counted.
2. Fixed expiry не сдвигается от accepted/denied повторов; reset только после DB expiry; valid Retry-After; missing/corrupt state/storage failure fail closed.
3. Настоящий canonical Better Auth HTTP request должен **действительно вызвать native sweep**: natural native bucket reset, disposable normal timestamps старше 60 s, Vico long-window record ещё жив. Проверить удаление expired native row, сохранение Vico count/expires_at и denial четвёртой target mail попытки до 600 s. Только исполнение вручную скопированного DELETE не является полной regression проверкой native seam.
4. Vico cleanup удаляет не более 64 expired rows, оставляет live/newly renewed и locked rows; второй client/barriers покрывает оба порядка cleanup↔renewal. Native `rate_limit` rows не меняются от Vico cleanup; repeated bounded batches делают прогресс. Native HTTP 3/10 s и 3/60 s limits/unknown-IP behavior остаются прежними, existing regression suites сохраняются.
5. Clean migrations и upgrade после `0073`, CHECK/PK/expiry-index/manifest parity; exact least-privilege positive budget SQL и negative localization/DDL/cross-domain probes на disposable PG17.
6. Согласованный correction head обязан пройти author self-check и применимые CI/acceptance. Старые green results ab2f09f — историческое evidence прежнего кода, а не PASS нового storage design.
