# DECISIONS.md — действующие решения задачи.

## D-01 — Concept before technical plan

Сначала формируется и принимается концептуальный план UI progress preview. Технический план реализации создаётся только после отдельного решения разработчика. Условие выполнено: концепция прямо принята владельцем, см. D-09.

## D-02 — No implementation during concept stage

До принятия концепции #322 не переделывается и новая preview implementation не начинается.

## D-03 — No predetermined winner

Текущая архитектура #322 и вариант production logic + substituted test infrastructure должны быть сравнены по фактам. Альтернативная модель не считается автоматически выбранной только потому, что выглядит проще. Сравнение завершено; владелец принял общий product code + внутреннюю test infrastructure с ограничениями D-06–D-08 (D-09).


## D-04 — Product logic should not be duplicated

Концептуальный план обязан рассматривать отсутствие второй реализации product behavior как основной критерий качества. Если production route/action/component может быть безопасно использован в preview, отдельная preview-версия того же поведения требует отдельного обоснования.

## D-05 — Test state is not required to be a real SQL database

Фраза «тестовая база в репозитории» означает детерминированное предметное состояние. Реальная embedded SQL/WASM база не является требованием; базовый вариант для сравнения — in-memory state + implementations production capability interfaces.

## D-06 — GitHub и браузер как единственная платформа

По прямому уточнению владельца всё необходимое для использования preview находится в GitHub: repository, Actions и Pages. Исполнение — в браузере. Внешние БД, отдельные hosts/servers и сторонние provider credentials не требуются.

## D-07 — Общий код интерфейса и application interactions

Preview использует фактические components/routes/application logic main. Изменение общей кнопки, ссылки или функции должно попадать в preview через пересборку без отдельной правки preview-экрана. Подменяются данные и инфраструктура, а не product UI.

## D-08 — Сохранение необязательно; simulated success разрешён

Владелец прямо подтвердил: проверяются все функции/interactions, кроме обязательного сохранения. Test storage не обязан изменять базу или сохранять данные после reload. Разрешено показывать «успешно сохранено» без реальной записи. Минимальный transient state допустим для проверки дальнейшего UI, но полноценный backend записи не требуется. Это уточнение отменяет искусственный persistence/SQL parity gate из прежнего предложения Лёвы, а не требование общего UI.

## D-09 — Концепция принята; Лёве поручен финальный технический PLAN

Прямое решение владельца: «Концепцию принимаю. Оформляй финальный технический PLAN.md на её основе».

Выбрана модель общего UI/routes/application interactions из main с fixture database и typed in-memory infrastructure в репозитории, только GitHub/браузер, с необязательным сохранением и разрешённым simulated success.

Канонический технический документ — PLAN.md; research/leva-chat-plan.md superseded. Поручение охватывает полный план, а не запуск P0/реализации, изменение #322 или deployment. Повторное принятие концепции не требуется. Следующая организационная работа Миры описана в WORKFLOW.md.
