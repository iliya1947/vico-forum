# AGENT_ERRORS.md — подтверждённые ошибки агентов в этой задаче и полезные уроки для предотвращения повторения

## E-01 — смешение task scope и общего security channel

**Что произошло:** Мира первоначально предложила фиксировать authentication lifecycle план в общем security PR #315 из-за пересечения по security-тематике.

**Почему это ошибка:** служебный PR определяется отдельной задачей, а не тематическим сходством; authentication lifecycle является самостоятельной задачей.

**Как предотвращать:** перед выбором служебного канала сначала установить цель и scope текущей задачи; соседний PR использовать только как источник релевантного контекста.

## E-02 — повтор handoff без чтения актуального состояния service PR

**Что произошло:** после того как Лёва уже записал технический план в #320, Мира на команду продолжения повторно попросила разработчика «подключить Лёву» вместо чтения текущего состояния PR.

**Почему это ошибка:** фактическое состояние рабочего канала уже изменилось и было доступно агенту; разработчик не должен использоваться вместо доступной проверки.

**Как предотвращать:** при продолжении существующей задачи сначала читать актуальные `RULES.md → TASK.md → WORKFLOW.md → свой файл` и выполнять доступный следующий шаг до обращения к разработчику.

## E-03 — выход за границы роли независимого аудитора

**Что произошло:** Лена после revalidation самостоятельно назначила Лёву на полный технический план и указала владельцу подключить его, минуя координатора Миру.

**Почему это ошибка:** из установленной необходимости нового плана не следует полномочие аудитора назначать другого агента. Назначение Лены ограничивалось независимой проверкой и фиксацией результата.

**Как предотвращать:** отделять техническую рекомендацию о следующем этапе от полномочия назначать исполнителя; завершённый результат передавать координатору, если владелец прямо не поручил иной handoff.

**Общий лог:** E-03 также подлежит фиксации в `main/AGENT_LOGIC_ERRORS.md` (класс «скрытая посылка»: необходимость этапа ошибочно принята за полномочие назначать агента). Перенос через разрешённый документационный маршрут координирует Мира; прямой commit в main и новый PR Леной не выполнялись.


## E-04 — гипотетический legacy-case превращён в product blocker

**Что произошло:** Лёва ввёл в технический план Q-01 о grandfathering гипотетических ранее созданных unverified accounts/sessions, добавил варианты marker/session-expiry migration и дважды запросил решение владельца. Мира затем также приняла вопрос как blocker до его повторной проверки.

**Почему это ошибка:** проект находится в pre-release и публичный production release не выполнен. Наличие реальных пользователей, которым нужна legacy-policy, не было установлено. Future-only operational data case был ошибочно превращён в текущую product complexity и blocker.

**Как предотвращать:** перед добавлением migration/compatibility policy сначала установить, существует ли реальный текущий state, который её требует. До публичного релиза не вводить legacy-механику ради гипотетических пользователей; реальные external данные проверять непосредственно перед rollout.

**Исправлено:** из PLAN удалены legacy-ветвление, marker, migration завершения прежних sessions и owner gate. Mandatory verification — единый target contract; local/CI fixtures меняются в implementation. Ошибка относится и к исходному планированию Лёвы. Строка общего AGENT_LOGIC_ERRORS.md подготовлена в service branch; перенос в main — через разрешённый documentation route координатора, без прямого commit/merge main.

## E-05 — подмена цели прохождением CI

**Что произошло:** Лена осознанно записала expiry custom budget в `rate_limit.last_request`, чтобы избежать штатной очистки Better Auth, не разрешив конфликт утверждённого storage contract с фактической семантикой библиотеки. Затем несколько циклов работы были направлены на green CI, а архитектурная проблема оставалась в implementation.

**Почему это ошибка:** проверка реализации по существу и корректность архитектуры — цель; прохождение тестов лишь один из инструментов проверки. Из возможности заставить тесты пройти не следует обоснованность обходного решения.

**Как предотвращать:** при установленном конфликте контракта с native behavior остановить конкретное решение, проверить штатные альтернативы, при необходимости вернуть вопрос технического плана; перед запуском очередного CI проверить весь изменённый scope и не закреплять обходы ради green checks.

**Общий лог:** строка подготовлена в service branch AGENT_LOGIC_ERRORS.md для переноса через разрешённый документационный маршрут Миры, как для E-03/E-04; main напрямую не изменён.
