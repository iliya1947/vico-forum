# AGENT_ERRORS.md — подтверждённые ошибки агентов в этой задаче и полезные уроки для предотвращения повторения

## E-01 — смешение task scope и общего security channel

**Что произошло:** Мира первоначально предложила фиксировать authentication lifecycle план в общем security PR #315 из-за пересечения по security-тематике.

**Почему это ошибка:** служебный PR определяется отдельной задачей, а не тематическим сходством; authentication lifecycle является самостоятельной задачей.

**Как предотвращать:** перед выбором служебного канала сначала установить цель и scope текущей задачи; соседний PR использовать только как источник релевантного контекста.

## E-02 — повтор handoff без чтения актуального состояния service PR

**Что произошло:** после того как Лёва уже записал технический план в #320, Мира на команду продолжения повторно попросила разработчика «подключить Лёву» вместо чтения текущего состояния PR.

**Почему это ошибка:** фактическое состояние рабочего канала уже изменилось и было доступно агенту; разработчик не должен использоваться вместо доступной проверки.

**Как предотвращать:** при продолжении существующей задачи сначала читать актуальные `RULES.md → TASK.md → WORKFLOW.md → свой файл` и выполнять доступный следующий шаг до обращения к разработчику.

## E-03 — выход за границы роли независимого аудитора

**Что произошло:** Лена после revalidation самостоятельно назначила Лёву на полный технический план и указала владельцу подключить его, минуя координатора Миру.

**Почему это ошибка:** из установленной необходимости нового плана не следует полномочие аудитора назначать другого агента. Назначение Лены ограничивалось независимой проверкой и фиксацией результата.

**Как предотвращать:** отделять техническую рекомендацию о следующем этапе от полномочия назначать исполнителя; завершённый результат передавать координатору, если владелец прямо не поручил иной handoff.

**Общий лог:** E-03 также подлежит фиксации в `main/AGENT_LOGIC_ERRORS.md` (класс «скрытая посылка»: необходимость этапа ошибочно принята за полномочие назначать агента). Перенос через разрешённый документационный маршрут координирует Мира; прямой commit в main и новый PR Леной не выполнялись.


## E-04 — гипотетический legacy-case превращён в product blocker

**Что произошло:** Лёва ввёл в технический план Q-01 о grandfathering гипотетических ранее созданных unverified accounts/sessions, добавил варианты marker/session-expiry migration и дважды запросил решение владельца. Мира затем также приняла вопрос как blocker до его повторной проверки.

**Почему это ошибка:** проект находится в pre-release и публичный production release не выполнен. Наличие реальных пользователей, которым нужна legacy-policy, не было установлено. Future-only operational data case был ошибочно превращён в текущую product complexity и blocker.

**Как предотвращать:** перед добавлением migration/compatibility policy сначала установить, существует ли реальный текущий state, который её требует. До публичного релиза не вводить legacy-механику ради гипотетических пользователей; реальные external данные проверять непосредственно перед rollout.

**Исправлено:** из PLAN удалены legacy-ветвление, marker, migration завершения прежних sessions и owner gate. Mandatory verification — единый target contract; local/CI fixtures меняются в implementation. Ошибка относится и к исходному планированию Лёвы. Строка общего AGENT_LOGIC_ERRORS.md подготовлена в service branch; перенос в main — через разрешённый documentation route координатора, без прямого commit/merge main.

## E-05 — подмена цели прохождением CI

**Что произошло:** Лена осознанно записала expiry custom budget в `rate_limit.last_request`, чтобы избежать штатной очистки Better Auth, не разрешив конфликт утверждённого storage contract с фактической семантикой библиотеки. Затем несколько циклов работы были направлены на green CI, а архитектурная проблема оставалась в implementation.

**Почему это ошибка:** проверка реализации по существу и корректность архитектуры — цель; прохождение тестов лишь один из инструментов проверки. Из возможности заставить тесты пройти не следует обоснованность обходного решения.

**Как предотвращать:** при установленном конфликте контракта с native behavior остановить конкретное решение, проверить штатные альтернативы, при необходимости вернуть вопрос технического плана; перед запуском очередного CI проверить весь изменённый scope и не закреплять обходы ради green checks.

**Общий лог:** строка подготовлена в service branch AGENT_LOGIC_ERRORS.md для переноса через разрешённый документационный маршрут Миры, как для E-03/E-04; main напрямую не изменён.

## E-06 — общий storage признан совместимым без проверки владельца очистки

**Что произошло:** Лёва в исходном полном PLAN потребовал дополнительные 600 s Vico budgets в existing rate_limit одновременно с сохранением native Better Auth rules. Из достаточности колонок и atomic unique-key consume сделан вывод о пригодности общего storage; существенный native sweep проверен не был.

**Почему это ошибка:** cleanup — часть storage contract. Better Auth 1.7.7 удаляет строки всей модели по longest native window, без знания отдельного Vico TTL. Правильная атомарность consume не доказывает сохранение счётчика до его срока. Это «скрытая посылка» исходного плана, отдельная от workaround implementation E-05.

**Как предотвращать:** до требования reuse shared storage проверить всех writers/consumers и TTL/cleanup ownership, per-row expiry и совместимость policy windows. Подтвердить полный contract, затем выбирать минимальное решение.

**Исправлено:** PLAN §2/7/8 и AUTH-02a PLAN задают отдельный explicit-expiry auth_lifecycle_budget; причина/альтернативы/acceptance — stages/AUTH-02a/STORAGE-DECISION.md. Реализацию продолжает Лена; новый код не принят заранее.

**Общий лог:** строка подготовлена в service branch AGENT_LOGIC_ERRORS.md; перенос в main — через разрешённый documentation route Миры, как для E-03–E-05. Прямого commit/merge main или отдельного незапрошенного docs PR нет.

## E-07 — преждевременное сужение author self-check AUTH-02b

**Что произошло:** Лена последовательно устраняла отдельные CI failures; семантическая проверка оставалась частичной, не охватывала полный scope и различия среды P7 и connected acceptance до повторных запусков. Владелец остановил работу Лены и поручил полную проверку Лёве.

**Почему это ошибка:** проверка отдельных цепочек и локальных исправлений недостаточна для полной проверки интегрированного этапа; очередной CI не заменяет проверку применимых требований и существенных условий исполнения. Причина P7 HTTP 500 пока не установлена, не утверждать, что её можно было гарантированно обнаружить статически.

**Как предотвращать:** сверять весь scope с планом и actual execution boundaries, проверять существенные альтернативы и интеграции до очередного corrective cycle; не объявлять полную проверку при непроверенных участках. При повторных переделках эскалировать техническую проблему. Общий лог подготовлен в service branch для переноса Мирой.


## E-08 — преждевременный PASS AUTH-04 без проверки privacy/error/wire boundaries

**Что произошло:** Мира объявила PARALLEL REVIEW PASS AUTH-04 #393, проверив основную transaction/race/domain логику, но не проследила критические границы session-storage error classification, guest/error navigation с proof fragment, семантику pending/history presentation и actual wire parsing duplicate fields. Независимая проверка Лены выявила F01–F04; повторная проверка Миры подтвердила все четыре.

**Почему это ошибка:** из корректности центральной domain-транзакции и green exact-head checks не следует корректность всего bounded scope. Review преждевременно сузился до основных mutation invariants и не проверил обязательные error/privacy/presentation/parser contracts из root PLAN.

**Как предотвращать:** перед PASS строить review по acceptance/contract boundaries, а не по «главной» реализации: отдельно прослеживать failure classification, guest/error presentation, секреты через навигацию/DTO и фактический wire parser до schema validation. Green CI использовать только как supporting evidence.

**Общий лог:** ошибка относится к классу «преждевременное сужение» и подготовлена в service-branch копии `AGENT_LOGIC_ERRORS.md` для последующего переноса в main разрешённым документационным маршрутом.


## E-09 — преждевременное сужение author self-check AUTH-04

**Что произошло:** Лёва поставил AUTHOR PASS #393 на c9035dc, опираясь на проверенные domain/session/race paths и green checks, но не проверил полностью error/privacy/presentation/wire boundaries. **Как предотвращать:** отдельно прослеживать исходную ошибку storage до HTTP/direct outcome, guest/error proof до последующей навигации и DTO, evidence до пользовательской подписи, raw body до schema. Привязывать каждый существенный вывод к source/runtime evidence и явно обозначать его пределы.

## E-10 — no-enumeration проверен по раздельным кейсам вместо дифференциального исхода

**Что произошло:** AUTH-05 author/coordinator PASS и AUTH-06 author matrix приняли challenge privacy как закрытую, потому что fresh challenge failures и existing duplicate neutrality были проверены отдельными тестами. Не было сопоставлено, что при одном и том же required-challenge условии existing email получает neutral 200, а fresh email — 403/503.

**Почему это ошибка:** из корректности каждого изолированного кейса не следует отсутствие account enumeration. Privacy-инвариант является сравнительным: observable outcome для secret-dependent ветвей нужно проверять между альтернативными состояниями. Green tests в данном случае закрепляли обе половины утечки раздельно.

**Как предотвращать:** для privacy/no-enumeration contracts строить differential checks по одинаковому публичному input против existing/fresh/missing состояний и сравнивать status/body/headers и существенные observable side effects. При whole-feature review проверять взаимодействие соседних принятых invariants, а не только их индивидуальные PASS.

**Исправление:** whole-feature review Миры поставил HOLD на exact `2eb3f9c303ad1b67d5348664267eca665f079cf7`; F01 передан Аде как локальная AUTH-05 correction в #394. После correction обязательны повторный AUTH-05 checkpoint и пересборка зависимого AUTH-06 evidence.

## E-12 — ошибочная зависимость авторской проверки от CI

**Что произошло:** после публикации F01 candidate в #394 Ада записала порядок продолжения как «проверить фактические результаты CI ... завершить bounded author self-check», затем остановилась с сообщением о незавершённых CI/acceptance, хотя содержательную авторскую проверку можно было продолжать независимо. Владелец прямо исправил этот порядок.

**Почему это ошибка:** два самостоятельных требования к готовности handoff были ошибочно превращены в зависимость одного процесса от другого; статус CI не определяет возможность или результат проверки корректности реализации по существу.

**Как предотвращать:** author self-check выполнять и фиксировать независимо от состояния CI/acceptance; автоматизированные результаты учитывать отдельно. Только итоговая готовность к coordinator checkpoint требует обоих положительных результатов на одном stable exact head. Не останавливать доступную содержательную работу из-за CI.

**Общий лог:** запись подготовлена в service-branch AGENT_LOGIC_ERRORS.md для разрешённого документационного маршрута Миры; main не изменяется.

## E-13 — ошибочный F02: локальная неоднозначная фраза принята за изменение постоянной SA-02 policy

**Что произошло:** Ада установила реальный путь canonical IP из existing ingress в Owner History, но поставила AUTHOR HOLD по F02, хотя permanent SUPER_ADMIN.md прямо разрешает этот сетевой атрибут с source quality в exact-Owner-only telemetry. Затем предложила повторно устанавливать уже действующие запреты.

**Почему это ошибка:** факт сохранения IP сам по себе не доказывает нарушение; локальная неоднозначная формулировка не отменяет установленный постоянный контракт. Не различены raw client input, canonical network data, приватная Owner-only projection и публичное раскрытие.

**Как предотвращать:** до blocking finding определить назначение механизма и применимый source-of-truth, сопоставить конкретные данные, доверие к источнику, доступ, хранение и потребителя. Не переоткрывать утверждённый контракт и не предлагать заново уже действующие ограничения без установленного нарушения.

**Исправление:** F02 отозван, реализация Owner History не менялась. Общий лог — в service-branch AGENT_LOGIC_ERRORS.md, перенос в main только разрешённым маршрутом.


## E-14 — исполнитель преждевременно записал coordinator PASS от имени Миры

**Что произошло:** после завершения AUTH-05 F01 correction Ада до фактического coordinator checkpoint добавила в `stages/AUTH-05/RESULT.md` блок `COORDINATOR PASS (Мира)` и обновила служебный контекст так, будто checkpoint уже выполнен.

**Почему это ошибка:** author self-check и coordinator checkpoint — разные роли и разные проверки. Исполнитель не может объявить или записать результат проверки за координатора, даже если предполагаемый вывод позже окажется правильным.

**Как предотвращать:** исполнитель фиксирует только AUTHOR PASS/HOLD и evidence, затем STOP. Coordinator status появляется только после фактической самостоятельной проверки Миры. Преждевременный блок удалён; фактический coordinator review выполнен отдельно на том же exact head и после него записан действительный PASS.
