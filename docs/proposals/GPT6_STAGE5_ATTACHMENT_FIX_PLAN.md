# GPT-6 — план исправления двух дефектов вложений (Stage 5)

**Статус:** предложение для соревновательного теста. Не реализация и не разрешение изменять код.

**Основание:** чтение реализации PR #215 на exact head `bb2d49eccf32efe8a300b4c88ccbeb5397998193` и действующего `EDITOR_SPEC.md`. Проверяемые дефекты относятся к существующему Stage 5. Этот PR содержит **только данный документ**, создан от `main`; PR #147 и PR #215 не изменяются.

## Цель

Исправить обе первопричины без обходных механизмов:

1. После явного выбора «Оставить серверную версию» не переносить вложения отвергнутой локальной версии и не допускать их повторного появления через запоздалые асинхронные ответы.
2. Повторные запросы одной подозрительной загрузки не должны создавать дубликаты в «Требуют внимания → Безопасность → Вложения».

Не расширять эту задачу до будущей публикации/скачивания вложений, очистки R2, антивируса, Stage 6 или реорганизации серверной модели поколений черновиков.

## Исправление A. Явный выбор серверной версии

### Первопричина

В `app/forum/use-editor-draft.tsx` функция `applyRemote()` при одинаковом текстовом `draftId` сохраняет прежнее `attachmentDraftId`. Это необходимо для **обычного чистого обновления** текста, но неверно для **явного отклонения** локальной версии. Сценарий A → Keep local с текстовым поколением B → конфликт в B → Keep server оставляет источник вложений A и может запустить A→B rebind.

В `app/forum/editor-attachments.tsx` состояние списка привязано к `owner/context/draftId`. При Keep server внутри B этот scope не меняется. Даже если очистить `attachmentDraftId`, проигравшие временные записи `uploading/error/ambiguous` сохраняются, а поздние ответы загрузок/GET/PATCH/DELETE могут обновить UI старой версии.

### Предлагаемый механизм

1. Разделить семантики `applyRemote`: автоматическое неконфликтное обновление может сохранить provenance в том же поколении; **успешный явный Keep server** записывает серверный snapshot **без attachment provenance отвергнутой версии**. Не выполнять сброс до успешной записи локального snapshot: ошибка локального сохранения не должна выдавать несуществующий принятый выбор.
2. В `useEditorDraft` ввести явный **selection epoch** (монотонный номер выбора состояния вложений), возвращаемый наружу. Увеличивать его при успешном Keep server, в том числе когда текстовый `draftId` остался B. Не увеличивать из-за фоновых metadata checks, обычного `attachmentRevision`, clean same-generation refresh или Keep local.
3. Передать selection epoch через `app/forum/markdown-editor.tsx` в `useEditorAttachments`. При смене выбора очистить только относящиеся к отвергнутому UI-состоянию transient entries, `removedIdsRef` и локальные статусы восстановлений/перепривязок; запросить **авторитетный GET** списка выбранного поколения. Не удалять серверные вложения на основании одного выбора текста.
4. Для GET/PATCH/DELETE и XMLHttpRequest upload фиксировать selection epoch в момент старта и проверять перед любым изменением состояния или вызовом callback редактора. Проверка только identity/`draftId` недостаточна. Запоздалый ответ прежнего выбора не может снова вставить файл, создать статус «Загружено», выполнить `noteAttachmentChange(B)` или завершить отвергнутый rebind в клиенте.
5. Уже начатую запись байтов в private R2 **не отменять** и не удалять по факту потери локальной версии. Позднее успешное завершение устаревшего UI-запроса может вызвать только повторное **авторитетное чтение** текущего выбранного поколения, не прямую вставку ответа. Файл виден в B только если серверная уже подтверждённая привязка/переадресация действительно делает B его каноническим поколением.
6. Сохранить действующие серверные ограничения: CAS целевой версии, сериализацию по owner/context, durable generation redirect и отсутствие ускоренного text sync. Не добавлять новые таблицы/endpoint для фиксации выбора серверной версии: найденная первопричина — неправильная клиентская граница выбора и callbacks.

**Существенный инвариант:** версию вложений определяет подтверждённая сервером принадлежность; локальная очередь запросов отражает только текущее решение пользователя, а не создаёт права на перенос вложений.

### Регрессионные проверки A

- Полная последовательность A → Keep local/B → несовместимое серверное обновление B → Keep server: локальный snapshot и исходящие PATCH не содержат переноса проигравшего A.
- Keep server внутри того же B с A in-flight, failed и ambiguous: старые записи не остаются и не возвращаются поздними ответами.
- Устаревшие GET/PATCH/DELETE/upload callbacks не меняют выбранное состояние. Корректно учитывается PATCH, уже успевший законно завершиться на сервере.
- Авторитетные refs B сохраняются; поздний A upload появляется в B **только** после допустимого ранее серверного redirect A→B и GET, но никогда как прямой результат старого XMLHttpRequest.
- Clean same-B refresh сохраняет вложения и текущие загрузки; Keep local сохраняет стабильные ID повторных запросов и исходное поколение.
- Обычный 60-секундный CAS text sync не меняется, немедленная загрузка его не запускает.

## Исправление B. Дедупликация событий безопасности

### Первопричина

Клиент повторяет подозрительную загрузку с тем же `X-Vico-Attachment-Id`, но `app/routes/attachment-upload.ts` при каждом отклонении передаёт `recordSecurityEvent({ uploadId: crypto.randomUUID(), ... })`. В `db/forum-attachments.ts` действует `ON CONFLICT (upload_id) DO NOTHING`, однако случайный ключ каждый раз другой. Удаление Retry либо подавление на стороне React не устраняет повтор после reload, конкурирующих запросов или потерянного подтверждения COMMIT.

### Предлагаемый механизм

1. Создавать **серверный стабильный ключ технического события** из канонически сериализованного набора:
   - namespace/версия алгоритма;
   - установленный сервером ID аутентифицированного пользователя;
   - нормализованный стабильный клиентский UUID загрузки;
   - исходные `contextKey` и `draftId`;
   - исходное имя файла **до** экранирования для хранения;
   - заявленные MIME и размер;
   - фактически установленный тип и причина отклонения.
2. Кодировать поля однозначным порядком и структурой (например, JSON-массив с версией и позиционными строками), вычислять SHA-256 средствами доступного Web Crypto. Ключ иметь явный собственный формат `attachment-v1:<hex>`, чтобы не спутать его с клиентским UUID или историческими значениями. Это ключ **идемпотентности наблюдаемого сигнала**, не хеш содержимого файла и не подтверждение безопасности.
3. Передавать этот ключ как `uploadId` в существующий `recordSecurityEvent`. Сохранить независимый генерируемый сервером первичный `id` события и существующую уникальность `upload_id`. В `validSecurityEvent` разрешить оба формата: исторические UUID и новый строго валидируемый ключ; старые записи оставить без обратной миграции.
4. Для одной и той же попытки и того же обнаруженного основания точные повторы, включая конкурентные, сходятся в одной записи по UNIQUE. Другой автор, контекст или фактически отличающееся свидетельство не должны подавляться лишь из-за совпадения пользовательского UUID. Не строить отдельную таблицу idempotency, mutex, очередь, React-кеш или новую миграцию.
5. Не изменять приватность отклонённых байтов, authz, выдачу файлов, сигнальную категорию, механизм загрузки и текущую будущую границу AV. Отдельно проверить, что представление модератора не предполагает, что внутренний `uploadId` обязательно имеет формат UUID.

### Регрессионные проверки B

- Два последовательных и два конкурентных идентичных подозрительных POST → **одна** запись события в PostgreSQL; оба остаются отклонёнными, доступного attachment ref/private object нет.
- Потерянный ответ успешной записи события и повтор → та же единственная запись.
- Одинаковый присланный UUID у разных пользователей → независимые записи.
- Изменение контекста, draft identity или объективно наблюдённого основания отклонения → разные события.
- Сохранение серверной генерации первичных `id`, исторических UUID-событий, ограниченных прав runtime и обычных 422/413/503 контрактов.
- Протестировать route→repository→native PostgreSQL UNIQUE/grants, не ограничиваться моками `recordSecurityEvent`.

5. Изменения ограничены текущим Stage 5; ничего не вносится в Stage 6, будущие publication/download/orphan cleanup slices.
