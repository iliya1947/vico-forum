## 1. Путь владельца и граница исполнения

В обычном чате владелец может спросить о состоянии форума, дать одну точную команду или подтвердить конкретное чувствительное изменение. Для чтения достаточно запроса. Для записи предлагается небольшая приватная форма **внутри того же чата**. Владелец вводит команду непосредственно в форму либо проверяет предложенный чатом черновик. «Выполнить» для обычной операции — единственное волеизъявление на запись. Для чувствительной операции первое действие запрашивает просмотр, второе подтверждает показанное сервером изменение. Вход в веб-панель форума нужен для первичной привязки или её возобновления после отзыва/истечения сессии.

Форма нужна по конкретной причине. GitHub подписывает доставку, но один и тот же автор и корректная подпись webhook возможны как у намеренной команды, так и у пересланной цитаты. В подтверждённом опыте #300 обычный ChatGPT передал через приватный GitHub три синтетические команды Actions. Опыт доказывает доставку. Он не устанавливает происхождение намерения владельца, пригодность его аккаунта для интерактивной формы или успешную работу production Worker. [Результат опыта](https://github.com/iliya1947/vico-forum/pull/300#issuecomment-7169600355) · [Граница исследования Worker](https://github.com/iliya1947/vico-forum/pull/300#issuecomment-7174975650)

Предлагаемый клиент — приватный персональный плагин, упакованный для ChatGPT Sites. Единственный доступный модели вход открывает компонент, передаёт черновик, запрос чтения или ссылку на результат. В компоненте действие «Закрепить тему T» подписывается при первой отправке. Чтение и показ результата остаются в обычном ChatGPT на имеющемся Plus. В Site достаточно описания инструмента и статического компонента. Там не нужны доступ к БД, ключ записи форума или ещё один сервер административных команд. Хостинг Sites включён в Plus по опубликованным условиям. Сборка и редактирование расходуют Codex usage, повседневное использование опубликованной версии отделено от сборки. Реальную доступность формы и лимиты на аккаунте проверяют при разрешённой активации. [Sites на Plus](https://help.openai.com/en/articles/20001339-creating-and-using-chatgpt-sites) · [Персональный плагин на Site](https://help.openai.com/en/articles/20001547-hosting-a-plugin-with-chatgpt-sites) · [Видимость инструментов и данных компонента](https://developers.openai.com/plugins/reference)

| Шаг | Что происходит |
| --- | --- |
| 1. Подготовка | Компонент отправляет аутентифицированное типизированное намерение по HTTPS на фиксированный вход Vico. Worker сохраняет временную запись и выдаёт одноразовую ссылку `requestRef`. Эта точка умеет только подготовить сообщение. Остановка до шага 2 оставляет форум без изменения. |
| 2. Доставка | Компонент передаёт в разговор только ссылку через штатный вызов хоста (например, `sendFollowUpMessage`). Штатное подключение GitHub в обычном ChatGPT публикует только версию протокола и `requestRef` в заранее привязанный inbox отдельного **приватного** репозитория. Основной сигнал — подписанный GitHub App webhook нового комментария. Ни #399, ни #400 для эксплуатационных данных не используются. |
| 3. Исполнение | Проверенный сигнал допускает запрос к единственному диспетчеру в Worker. Тот загружает ранее сохранённое намерение, заново устанавливает полномочия и вызывает фиксированный защищённый reader или каноническую команду. Подготовка и исполнение имеют разные точки входа. Диспетчер принимает только заявку с подтверждённой доставкой GitHub. |
| 4. Обратная доставка | После получения доменного исхода Worker публикует в том же inbox короткий ответ своего GitHub App с `commandId`, фазой и `resultRef`. Чат читает ответ. Компонент предъявляет ссылку и доказательство действующей привязки, сервер проверяет происхождение конкретного ответа GitHub и выдаёт разрешённую проекцию сохранённого результата. Чтение `resultRef` никогда не запускает доменную запись. |
| 5. Ожидание | Пока ответа нет, чат показывает «ожидается результат» и ID. Ограниченный опрос или последующий запрос статуса продолжает чтение той же операции. Отсутствие ответа не превращается в новую попытку записи. |

Таким образом приватный GitHub участвует в обоих направлениях. Большие заметки, тексты жалоб, причины, доказательства и приватные ответы не требуется размножать в комментариях, истории редактирования, Actions logs или artifacts. Передача ссылок через другую issue, другой репозиторий или чужой чат не выдаёт данные и не меняет адрес ответа.

## 2. Кто вправе выдать команду

1. **Привязка.** Компонент создаёт неизвлекаемый ключ подписи Web Crypto P-256 и хранит его как CryptoKey в IndexedDB собственного изолированного origin. При потере ключа требуется новое сопряжение. Одноразовое сопряжение открывается на фиксированном HTTPS-origin форума. После действительной Better Auth сессии сервер проверяет `isBoundOwner(session.user.id, VICO_OWNER_USER_ID)` и активный AccountState. Владелец сверяет код сопряжения в форме и на форуме. Одноразовый challenge, доказательство владения ключом, same-origin POST, защита от CSRF, одноразовый state и срок 5 минут связывают одобренный публичный ключ с этой сессией. Автоматическое добавление ключа по ссылке, email, роли или GitHub login запрещено. Приватный ключ и bearer/cookie сессии остаются на своих сторонах. [Web Cryptography API](https://www.w3.org/TR/WebCryptoAPI/)
2. **Что хранит сервер.** У привязки есть случайный ID, публичный ключ и его версия, внутренний user ID и ID сессии Better Auth, который сам по себе не даёт входа, срок, признак отзыва, назначение подписи (audience) и числовые ID приватного канала GitHub. На чтении, подготовке, preview, исполнении, статусе и выдаче данных проверяются актуальные привязка, сессия (принадлежность, существование, срок), состояние аккаунта и точное совпадение с текущим Owner binding. Канал не продлевает сессию. Смена Owner, отзыв ключа, выход или удаление сессии закрывают доступ и старые подтверждения. Ротация требует новой привязки действующим владельцем. Утрата устройства закрывается отзывом на форуме.
3. **Граница намерения.** Чат может открыть форму и заполнить **черновик**. Только обработчик явной отправки в изолированном компоненте подписывает `execute`, `preview` или `confirm`. Автозапуск при открытии, сообщения от модели, повторный рендер и изменение данных не вызывают этот обработчик. Компонент сам строит подпись из видимых типизированных полей. Он не подписывает переданные извне байты, произвольный digest или скрытые поля. Путь `read/status` подписывает только собственную фазу и закрытый набор readers, без подтверждения. Сервер проверяет подпись независимо от видимости инструмента для модели. Произвольный MCP/HTTP-вызов с данными GitHub, идентификатором привязки или read-подписью не даёт права записи.
4. **Источники данных.** Тексты форума, профили, названия, Markdown, notes, evidence, History, содержимое GitHub и результаты инструментов отображаются как данные. Свободный текст может быть значением объявленного поля, например причиной Hide. Он не разбирается как следующая команда. Фиксированные подписи кнопок, вид операции, ID цели, причина и эффект выводятся раздельно. Нет исполняемого HTML, автоматического перехода по внешней ссылке, вызова инструментов из результата или выбора получателя через текст. Компонент ограничивает CSP и список сетевых origin. В модель уходят только явно разрешённые поля результата. Служебные challenge и материалы ключа исключены из transcript и tool output.
5. **Серверный actor.** После всех проверок используется user ID связанной живой сессии. Входные `actorId`, permission, role, произвольные URL, SQL, shell, списки команд и неизвестные поля отклоняются. Изменение чужих credentials/сессий, реактивация или hard delete аккаунта, личные настройки, передача Owner и автономная модерация отсутствуют в реестре v1. Канал использует существующие `app/authorization/owner.ts`, `db/account-state.ts`, permission resolver, AP-10 и проверки ресурса. Текущие правила exact Owner, включая собственную иерархию/иммунитет, применяет домен. Отказ или недоступность источника полномочий закрывает вызов до раскрытия цели.

## 3. Протокол, подтверждение и результат

У протокола есть явная версия, закрытый реестр имён и схема для каждого имени. В реестре описаны тип цели, обязательные параметры, допустимые фазы, область разрешения, защищённая проекция, функция определения риска и канонический обработчик. Отсутствие записи означает отказ. Свободный перевод фразы в черновик заканчивается до этой границы.

| Сообщение | Минимальные поля и смысл |
| --- | --- |
| Запрос | `v, audience, bindingId, keyVersion, commandId, requestId, phase, issuedAt, expiresAt`, затем `op, target, args` и применимые `expected`. Для `confirm` передаются только ссылка на серверный preview и его digest, для `status` — ссылка на прежнюю команду. Каждое волеизъявление имеет UUID, повтор доставки сохраняет ID и содержание. Repo/inbox и назначение фазы входят в подписываемые данные. |
| Нормализация | В конверте передаётся отдельная подпись ES256 зарегистрированным ключом. Подписываются UTF-8 байты проверенной по схеме структуры в каноническом представлении RFC 8785. Поле подписи отделено от подписываемых полей. Дубликаты ключей, неоднозначные типы, лишние поля и некорректные ID отвергаются до сохранения. Счётчики PostgreSQL bigint передаются канонической десятичной строкой. Лимит тела 128 КиБ дополняет существующие доменные пределы для отдельных полей. |
| Preview | Неизменяемый серверный снимок связывает привязку/сессию, `commandId`, операцию, точную цель, параметры, прежнее состояние и его версию, запланированное изменение и последствия. Для Create указываются родитель/коллекция и имя. Для доступа показывается дельта, для регистрации — оба флага, для Restore — повторная публикация. У заметки/причины подтверждается весь текст, включая возможность раскрыть длинное значение. |
| Confirm | Форма получает preview через проверенный ответ, отображает сохранённые серверные поля и только по отдельному действию владельца подписывает свежую фазу `confirm` с `previewId` и digest. Сервер загружает собственный снимок. Текст «да», label, reaction, флаг `confirmed` и новое тело операции его не заменяют. Одно подтверждение относится к одной команде, одной привязке и одной версии ресурса. |
| Сроки | Исполняемый запрос и preview действуют максимум 5 минут каждый, не дольше живой привязки и сессии. Время сравнивается по серверным часам повторно перед эффектом, с ограничением будущего `issuedAt` до 30 секунд. Повтор сообщения не продлевает срок. Изменение параметров, затронутого состояния или привязки требует новой явной команды, для sensitive — нового preview. |
| Ответ владельцу | `commandId, phase, op, target, status`. Для чтения добавляются разрешённые `data, asOf, coverage, nextCursor` по необходимости. Для записи — `changed`, фактический исход домена и версия/ID события, если их возвращает операция. Служебный ответ в GitHub содержит только корреляцию и ссылку на доставку. Номер HTTP, webhook ACK и результат Actions job не используются как признак применения. |

Байты подписи и фазовые поля должны совпадать между браузером и Worker в опубликованных тестовых векторах, включая русский, иврит, перестановку полей, `null` и большие версии. [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) · [RFC 7518, ES256](https://www.rfc-editor.org/rfc/rfc7518#section-3.4)

## 4. Подключение к возможностям main

В `workers/app.ts` уже собираются request-scoped readers/writers и раздельные `WEB_HYPERDRIVE` / `HYPERDRIVE`. Общий `app/routes/api.ts` отвечает 404. Выделить только необходимые узкие функции из route guard/action и вызывать их из браузерного маршрута и нового адаптера. Сохраняются существующие origin/CSRF/session-проверки HTTP-маршрутов. Новый вход получает собственный проверенный контекст. Поддельный `Request`, установка `authSessionContext` из конверта, HTTP-проксирование форм и прямое чтение/изменение доменных таблиц из транспорта исключены.

### Запись

Риск вычисляет сервер по зарегистрированной операции **и фактическому эффекту под доменной блокировкой**. При появлении чувствительного эффекта обычный запрос может вернуть только preview или `conflict/stale`. Если владелец указывает на ранее показанное состояние, команда несёт его версию. Для самостоятельной обычной команды с точной целью и без переданной версии обработчик один раз получает текущие исходные значения из защищённого reader и передаёт их в каноническую проверку при записи. На конфликте эта цепочка останавливается. При confirm все динамические проверки выполняются заново.

При деактивации связать UUID с original Owner event и проверять цель/self. |
| Registration | — | Включение/выключение любого из двух видов новых регистраций | `app/routes/settings-forum.tsx` → `db/registration-settings.ts`. Команда меняет запрошенный флаг, переносит второй из снимка и передаёт штатный `expectedVersion`. Одновременное изменение веб-панелью даёт конфликт. |
| Complaints | Установить/снять priority override одного open Case | Append private note, initial Decision `confirmed/not-confirmed`, resolve Appeal `upheld/overturned`, изменить глобальные reason weights | `db/complaints-service.ts` / `db/complaints-repository.ts` и существующие queue/review/appeal capabilities. Сохранять operation identity, Case/settings version, проверку pending/immutable, нативные события и уведомления. В `docs/moderation/COMPLAINTS.md` другой reviewer предпочтителен, но тот же имеющий право reviewer допустим. Канал никогда не переключает actor ради второго reviewer. |

Два случая определяют устройство адаптера. `removeHelpDuplicate` в `main` принимает существующую pending appeal в той же транзакции. Для обычного снятия ожидаемое отсутствие appeal проверяется под теми же locks, что и её создание. Если она появилась, отношение остаётся прежним, а новый preview показывает и снятие, и принятие конкретной appeal. Проверить также изменения Help, закрывающие pending signals как `superseded`. Для сохраняемого терминального исхода preview охватывает изменяемое множество и его версию. Это один существующий доменный эффект. Второй цикл по сигналам и второй History writer здесь не нужны. [Контракт History в main](https://github.com/iliya1947/vico-forum/blob/c49897181388b4a78f8e8248dc6508551df576c4/docs/ADMIN_PANEL.md#L582-L607)

Второй случай — `renameCustomRole` и другие authorization writes. У общего mutex есть сериализация, но публичная форма сегодня не передаёт `expectedVersion`. Проверка перед вызовом writer оставила бы окно для параллельной записи. Для каждого метода зафиксировать релевантные зависимости preview. Использовать нативную монотонную версию, immutable ID или версию коллекции там, где они уже есть. Если такой версии нет, канонический writer проверяет новую precondition под своим lock. Ревизию при фактическом изменении обновляют **все** штатные входы. Для ролей допустим один счётчик на существующем `authz_mutation_lock`. Для note/appeal использовать реальную версию Case/pending ID. Хеш двух одинаковых значений сам по себе пропускает последовательность A→B→A. Тест старого preview должен ловить её и создание/удаление связанного объекта. Изменение, расходящееся с показанным эффектом, завершает старую попытку. Новых исполнительных возможностей RBAC или новых исходов домена это не вводит.

## 5. Атомарность, повтор и потеря ответа

Состояние канала хранится в существующей PostgreSQL. Достаточно записи привязки и записей запросов/результатов по фазам одной логической команды. Временные аргументы, preview, данные для выдачи и отметка о доставке могут быть полями этих записей. Декларативная миграция обновляет Drizzle schema/journal/snapshot, структурный manifest и точечные web ACL по существующему порядку. Доменная History остаётся в своём исходном источнике.

1. Ключ логической операции — `(audience, bindingId, commandId)`, ключ доставки фазы — `requestId`. Контрольный digest связывает нормализованные `op/target/args/expected` с привязкой. Идентичный повтор подготовки возвращает ту же ссылку. Для confirm используется отдельный requestId при том же commandId. Дубли и обе транспортные ветки сходятся в одной записи. Коллизия ID с другим содержанием даёт конфликт, исходная запись остаётся неизменной.
2. Проверенный webhook сначала **долговечно** переводит запрос из подготовленного в принятый. Только затем допустим быстрый `202`. После него Worker может продолжить короткую обработку через `waitUntil`. Пробуждение можно потерять, поэтому первичным источником стадии остаётся строка в БД. Только доказанно ещё не начатый принятый запрос в пределах срока допускается к первому запуску. Статус сам не запускает команду.
3. Первый исполнитель атомарно переводит заявку в состояние «начата» с уникальным номером попытки. Каноническая транзакция может продолжиться только с этим номером. Сверка, которой требуется закрыть попытку, берёт ту же блокировку строки и аннулирует её номер. Задержавшийся исполнитель после этого не сможет начать или закончить новый эффект. В транзакции канонического writer он удерживает строку операции, повторно проверяет право исполнения, срок, привязку и версию/эффект под штатными locks, потребляет confirm, фиксирует эффект, штатную History и минимальный результат. Всё коммитится или откатывается вместе. Повторно употребить confirm через другой `requestId` нельзя. Отзыв привязки и исполнение сериализуются, после завершённого отзыва новый эффект невозможен.
4. В `main` одни writers владеют `pg`-транзакцией, другие — `Drizzle.transaction`. Подключить узкую операцию записи квитанции к **этому же** client/tx. Встроенные operation ID/отпечатки Complaints, AP-10 и деактивации переиспользовать, для создания меры её create UUID играет роль ID. Для pin, структуры и остальных команд без подходящей квитанции добавить такой же транзакционный путь в существующую функцию. Внешний `BEGIN` вокруг writer с другим соединением, запись успеха после возврата из writer и поиск последнего похожего события не обеспечивают атомарность. Сохранить порядок domain/actor/History locks и сроки запросов. Фиксация квитанции не берёт новых доменных locks после History. Внутри транзакции нет вызовов GitHub.
5. Финальная запись содержит `changed` и минимальные ID/версии или ссылки на существующее событие. Допущенный доменом no-op возвращает `committed, changed=false`. Повтор возвращает прежнюю квитанцию только после новой проверки доступа. При возобновлении публикации Worker сначала находит ранее созданный ответ своего App по `commandId/phase/resultVersion` и при необходимости обновляет его. Даже две одинаковые публикации после потери ответа POST обозначают один результат.
6. Временное тело живёт до отказа, исполнения или истечения запроса, затем удаляется. Приватная выдача и подробный preview доступны максимум 15 минут и 5 минут соответственно. Для больших результатов выдавать страницу в пределах доменных лимитов. Минимальный receipt доступен для сверки 30 дней. Дальше достаточно tombstone ID/digest в пределах жизни привязки плюс максимальное окно подписи. Удалённые ссылки не создаются заново из старого сообщения, истёкшая подпись не может начать исполнение. Очистка идёт ограниченными порциями. Секреты сессий/провайдеров, сырой payload, история прочитанных текстов и содержимое файлов в receipt не пишутся.

| Наблюдаемое состояние | Что возвращать и какое действие допустимо |
| --- | --- |
| Чтение завершено / preview готов | `read-ok` с разрешённой проекцией, в том числе с частичным покрытием, либо `preview-required`. Доменная запись ещё не выполнена. |
| Доставка принята, финала нет | `pending` и ID, затем запрос статуса. «Комментарий создан», `2xx`, зелёный job и желаемое значение поля сами по себе не доказывают эффект. |
| Квитанция подтверждает commit | `committed` с целью, `changed` и фактическим результатом, включая реальный терминальный исход. |
| Допуск или ввод отклонён | `not-committed/denied` с безопасной причиной. В частности, неоднозначный target, неподдерживаемая операция, невалидное подтверждение и закрытый ресурс не раскрывают приватное состояние. |
| Версия, preview или содержимое по тому же ID расходятся | `conflict/stale`. Получить свежую защищённую проекцию. Только новое явное действие может создать новый запрос и требуемый preview. Автоматического обновления версий с повтором записи нет. |
| Известно, что эффекта не было | `unavailable` при недоступной зависимости до начала вызова, доказанном rollback или отказе по бюджету до исполнения. Если транспорт не знает, был ли запрос принят, он не вправе присвоить этот исход. |
| Потеря соединения при COMMIT, таймаут после передачи или исчезновение исполнителя в неизвестной точке | `outcome-unknown`. Приоритет имеет подтверждённая квитанция с первичного хранилища или точное каноническое событие с тем же actor/operation ID/digest. После завершения старой попытки либо аннулирования её номера под блокировкой подтверждённый rollback можно показать как отсутствие эффекта. До доказательства оставлять unknown. Не отправлять запись повторно, не выдавать новый ID и не передавать исполнение в Actions по истечении lease. Поздний достоверный commit заменяет наблюдение unknown. |

## 6. Доставка, бюджет и отключение

- **Worker.** Принимать только HTTPS, один настроенный GitHub App/installation, приватный репозиторий по числовому ID, настроенный inbox issue и допустимого отправителя. Проверять `X-Hub-Signature-256` по ограниченным исходным байтам до разбора. Проверять тип события, действие `issue_comment.created`, принадлежность источника и согласованность фазы со staged request. Изменение комментария, PR, fork, посторонний файл и ответ самого App не являются новым входом. `X-GitHub-Delivery` пригоден для диагностики и фильтра дублей доставки. Идемпотентность эффекта даёт `commandId`. Подтверждение приёма укладывается в 10 секунд, длинный нативный Overview заканчивается независимо от HTTP ACK. [Проверка подписи](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries) · [Ограничения доставки](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks) · [Сбой webhook](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries)
- **Actions.** В репозитории проекта готовится выключенный шаблон явно запускаемого workflow для приватного транспорта. Для вызова из обычного чата GitHub connector создаёт в том же приватном репозитории служебную issue, содержащую только ID исходного комментария inbox, и по явной команде ставит выделенную метку. Событие `issues.labeled` с этой меткой запускает короткий job на стандартном Linux. Job читает исходный комментарий из закреплённого inbox и передаёт ссылку в тот же Worker. Доступность `workflow_dispatch` из чата не требуется. Метка разрешает доставку и не подписывает волеизъявление. Для доставки — GitHub OIDC с отдельным `aud`, проверкой issuer/JWKS, времени, repo/owner ID, разрешённого workflow/ref из доверенной ветки и события. Worker сам проверяет исходное сообщение через installation API. Job не получает forum credential, SQL-доступ или ключ владельца. Минимум прав — `issues:read` и `id-token:write`. Ответ публикует Worker краткоживущим installation token, ограниченным одним репозиторием и правом на Issues. Ни checkout пользовательской ветки, ни исполнение содержимого issue не нужны. [События Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#issues) · [OIDC claims](https://docs.github.com/en/actions/reference/security/oidc) · [Installation access](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation)
- **Переключение.** При потере webhook и доступных GitHub, Worker/API и БД владелец может явно доставить ту же заявку после проверки статуса. При proof «уже committed» восстанавливается только выдача. При неизвестном исходе доступна только сверка. Одновременная доставка из обоих входов безопасна. При общей недоступности GitHub, Cloudflare, Hyperdrive или БД резерв ждёт восстановления. Дополнительные тяжёлые вычисления не требуются ни одной операции v1.
- **$0.** По умолчанию вход закрыт, нет фонового polling каждой issue, постоянных runner, новых платных сервисов и модельного API. Ограничить размер, страницы, число ожидающих команд на привязку, число операций и повторов выдачи в окно, время выполнения и параллелизм. До затрат резервировать из ограниченного счётчика дневной бюджет канала с запасом для основного форума. Стандарт Free Worker публикует 100 000 запросов в сутки на аккаунт, 10 мс CPU и 50 subrequests на вызов. Hyperdrive Free публикует 100 000 SQL statements в сутки. GitHub compute делится с другой работой. Это верхние лимиты провайдеров. Доступный остаток подтверждается отдельно. Выделять бюджеты ниже фактических бесплатных остатков с жёстким ограничением расходов у провайдера. Эксплуатационный workflow включают только при действующем внешнем жёстком лимите без overage. Локальный счётчик не может предотвратить оплату уже начавшегося job. Неизвестный остаток для дополнительного runner или отсутствие гарантии остановки за $0 закрывают этот путь. При исчерпании бюджета показывать `unavailable` до запуска, без платного fallback. [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) · [Hyperdrive Free](https://developers.cloudflare.com/hyperdrive/platform/pricing/) · [GitHub included usage](https://docs.github.com/en/billing/reference/product-usage-included) · [Neon plans](https://neon.com/docs/introduction/plans)
- **Отключение.** Выключатель ingress и отзыв привязки прекращают допуск новых команд и подтверждений. Уже начатая транзакция имеет один проверяемый исход. Доступ к ранее полученному результату снова проходит актуальные права и защиту целевой проекции. В технических логах допустимы корреляция, тип фазы, классификация сбоя и длительность. Ответы и ошибки приватны, `no-store`.

**Предложение Мире — stacked-поставка от #399.** A и B вводят границу доступа, D делает безопасной запись, E–H её используют. Промежуточный merge не даёт владельцу законченный v1. C и D, затем E–H технически могут проверяться ограниченными diff, хотя команда ведёт их последовательно. Решение о режиме принимает Мира после проверки плана. Для stack — отдельная ветка/PR на ступень поверх предыдущей, author self-check, применимые checks и checkpoint Миры на точном head. При изменении основания синхронизировать зависимые ступени. В конце собрать итог в #399, закрыть промежуточные PR как superseded, пройти self-check, whole-feature review Миры и независимую проверку Лёвы на том же stable head. Merge выполняет владелец. Если Мира выделит самостоятельно поставляемый этап, для него действует полный цикл отдельного implementation PR до начала зависимого этапа. Постоянную документацию и `PROJECT_STATE.md` обновляют отдельным docs PR по фактическому итогу.

## 8. Матрица repository/local-CI acceptance

Использовать реальный built Worker, disposable PostgreSQL 17 с миграциями и web ACL, Better Auth сессии и Chromium. GitHub inbox/App, webhook и OIDC/JWKS воспроизводятся локальными транспортными fixtures с тестовыми ключами. Подменяется внешняя доставка. Чтение, авторизация, CAS, записи, транзакции и History выполняет приложение. Каждой записи реестра соответствует позитивный пример и проверяемая ссылка на канонический вызов. В наборе есть HTTP/UI-проверки нормальных точек входа. Существующие наборы `tests/database`, `tests/browser` и тесты route/actions используются как отправная точка.

| Критерии scope, раздел 11 | Вход и ожидаемый результат |
| --- | --- |
| 1, 8. Полнота чтения | Автоматическое сравнение фиксированного списка capability с матрицей. Подключить новый suite к существующим path-фильтрам. Для PR действуют одноразовые `run:ci` / `run:acceptance` по `AGENTS.md`. Приёмка требует сверить фактическое выполнение нужного suite на том же head. Список выше задаёт будущие проверки. Статус планирования не означает их PASS.

## 9. Stage 6

Только по отдельному явному разрешению владельца — проверка актуальных планов/бюджетов и остатка общих квот, реальная Better Auth Google-сессия и привязка `VICO_OWNER_USER_ID`, применение миграций и web grants, production bindings, секреты/ротация GitHub App/webhook, подключение выделенного приватного inbox, публикация и подключение приватной формы на аккаунте Plus, разрешённый выпуск Worker и включение резервного workflow. Секреты вводятся в штатные secret stores. Сначала сверяются режим приватного репозитория, разрешения интеграций, работа штатных инструментов GitHub в обычном чате, изоляция ключа в реальном компоненте и доступный бесплатный бюджет. Включение начинается с чтения и проверки, что итог действительно виден владельцу в чате. Только в пределах данного разрешения проверяются явная обратимая операция, состояние домена, History, восстановление результата и отключение канала. У deployment есть отдельный выключатель и отзыв привязки.

Внешняя пригодность сочетания «личный Site-плагин + изолированная форма + приватный GitHub» для конкретного аккаунта и реальная нагрузка Worker пока **не проверены**. Если платформа не обеспечивает изоляцию подписанта или гарантированный $0, запись остаётся выключенной, а владельцу возвращается конкретное ограничение. Создания внешних ресурсов и отдельного исследовательского Worker PoC для подготовки или принятия этого плана не требуется.
