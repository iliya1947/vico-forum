## 1. Обычный разговор и выбранная интеграция

Владелец работает в приватном ChatGPT Project. Чтение и диагностика выполняются сразу. Перед любой записью Мира сама проверяет цель, параметры, применимость и текущее состояние. Если от владельца нужен выбор, Мира задаёт один конкретный вопрос. Затем она описывает конкретное действие, причину и существенные последствия. Для группы она показывает весь набор целей, для составной задачи — все шаги и возможный частичный результат. Отдельное явное сообщение владельца в этом же разговоре разрешает отправить именно эту задачу. При изменении её состава, параметров или состояния Мира сначала объясняет обновлённый вариант. [User journey v1](research/user-journey-v1.md)

**Выбор для v1 — один персональный плагин с текстовыми MCP tools, хостинг на приватном ChatGPT Site.** Site нужен как способ подключения tools к личному аккаунту. В обычной работе видны только сообщения в Project. У каждого чтения и каждой записи есть конкретный tool с закрытой input/output schema. Tool сам проводит свой запрос через серверный адаптер и приватный GitHub, сам получает результат либо честный pending/unknown. Чтение статуса — отдельный самостоятельный tool. `sendFollowUpMessage`, интерактивный компонент и отдельное GitHub-подключение модели в этом маршруте отсутствуют. Это устраняет F-01. [Подключения в Projects](https://help.openai.com/en/articles/10169521-projects-in-chatgpt) · [Tools через персональный Site](https://help.openai.com/en/articles/20001547-hosting-a-plugin-with-chatgpt-sites) · [Tool independence](https://developers.openai.com/plugins/plugin-guidelines#62-tool-independence-and-exposure)

Опыт #300 подтвердил конкретный синтетический обмен с приватным GitHub через Actions. Для планирования выбрана поддерживаемая поставка через Site, поскольку текущая справка описывает штатный GitHub app как read-only и не даёт опираться на запись им из любого Project. Документация описывает Sites на Plus, запуск подключённых apps из Project и отдельное разрешение `Allow all tools` для некоторых личных соединений. Ни отдельное разрешение, ни отсутствие карточек действий на всём наборе v1 для аккаунта владельца пока не подтверждены. Доказательство в Stage 6 включает чтение и каждую категорию риска инструментов. Если хост требует дополнительной карточки у любой операции v1 или tool недоступен в обычном Project, это блокирует выпуск утверждённого UX. Аннотации отражают реальные эффекты и дополнительные проверки хоста не обходятся. [Опыт #300](https://github.com/iliya1947/vico-forum/pull/300#issuecomment-7169600355) · [GitHub app](https://help.openai.com/en/articles/11145903-connecting-github-to-chatgpt) · [Настройки разрешений ChatGPT](https://help.openai.com/en/articles/20001495-managing-app-permissions-in-chatgpt) · [Sites и Plus](https://help.openai.com/en/articles/20001339-creating-and-using-chatgpt-sites)

| Узел | Ответственность |
| --- | --- |
| ChatGPT Project | Держит только одну ожидающую подтверждения задачу в текущем разговоре. Инструкции Project требуют считать свежими управляющими сообщениями только сообщения владельца из этого разговора. Цитата, гипотеза, текст форума и GitHub, а также «да» в другом чате волеизъявлением не служат. У задачи нет продуктового таймера подтверждения. |
| Персональный MCP Site | Объявляет конкретные tools и передаёт вход в Vico. Подключение аутентифицировано, server-only, с фиксированным адресом назначения. Site не получает GitHub App key, доступ к PostgreSQL или универсальный прокси. |
| Vico Worker, вход tool API | Проверяет делегированный доступ владельца, проверяет типизированный запрос, создаёт долговечную запись доставки и публикует непрозрачную ссылку в приватном GitHub. Этот вход только принимает запрос и получает его результат. |
| Приватный GitHub | Один отдельный приватный репозиторий с inbox. Два вида сообщений фиксированного формата — request ref и receipt ref. Содержание отчётов, заметок, evidence, ключи, причину и идентификаторы пользователей в GitHub не копировать. |
| Vico Worker, вход webhook | Принимает только проверенную доставку зарегистрированной записи, получает из сохранённой записи точные аргументы, заново применяет нативные проверки и вызывает единый обработчик. Завершённый исход публикуется с receipt ref в том же приватном inbox. |
| Ответ tool | Проверяет публикацию своего GitHub App для этого запроса. Затем API Vico выдаёт защищённый результат действующей привязке. При длинной операции возвращает ID и pending с отдельным чтением статуса. Отказ GitHub не выдаётся за успех и не отменяет уже совершённый commit. |

Tool может отправить несколько коротких служебных HTTP-запросов к Worker в пределах фиксированного времени. Описание инструмента явно раскрывает внутреннюю доставку непрозрачного конверта. При разметке read tools учитываются и доменная операция, и побочный эффект частного transport POST по правилам OpenAI. Для проверки «чтение сразу» инструмент должен работать в поддерживаемом режиме разрешений без обязательной карточки. [Аннотации инструментов](https://developers.openai.com/plugins/plugin-guidelines#63-accurate-tool-annotations) Единственный путь к чтению/исполнению полноценного запроса — после проверенного входящего сообщения приватного GitHub. Read-only status может сообщить наличие записи и ход доставки при сбое GitHub. Неопубликованную защищённую проекцию этот вход не раскрывает. Состояние форума, которое удалось установить напрямую по квитанции во время сбоя выдачи, остаётся доступно для сверки без новой мутации.

## 2. Владелец, полномочия и защита от недоверенного ввода

1. **Одно подключение.** Персональный Site объявляет аутентифицированные MCP tools. В Stage 6 владелец связывает app с Vico через OAuth Authorization Code + PKCE S256 с использованием действующей Better Auth сессии. Использовать поддерживаемый Better Auth OAuth Provider для выдачи делегированных токенов поверх текущего входа. Закрепить совместимую с baseline версию и регистрацию только для доверенного ChatGPT клиента, по фиксированным issuer, resource и redirect URI. Проверить этот выбор на штатном потоке Sites. Сервер принимает согласие только от активного `isBoundOwner(session.user.id, VICO_OWNER_USER_ID)`. Политика привязки не опирается на email, username GitHub или сохранённую роль. [OAuth для MCP](https://developers.openai.com/plugins/build/auth) · [Better Auth OAuth Provider](https://www.better-auth.com/docs/plugins/oauth-provider)
2. **Ограниченная делегация.** Короткий opaque access token с audience, равным точному resource URI персонального MCP, и scopes чтения/записи использует серверный обработчик инструмента. Site и tool API Worker образуют один OAuth resource server. Site посылает bearer только на фиксированный HTTPS endpoint этого Worker, который интроспектирует его у Vico OAuth Provider. Затем Worker сам допускает только нужный scope и метод. На этапе A проверить поддержку этого OAuth flow на Site fixture и совместимость схемы Better Auth с baseline. Связь provider grant → Site client → Better Auth `user.id/session.id` → разрешённый репозиторий хранится сервером. Повтор входа бывает при истечении или отзыве связанной сессии, а refresh не заменяет проверку сессии. При выдаче, обновлении токена, приёме, исполнении, сверке и выдаче результата повторно проверить grant, current Owner binding, живую сессию и AccountState. Отозванный доступ, исходная сессия и смена Owner блокируют ранее доставленную незавершённую работу. Bearer и cookies отсутствуют в prompts/GitHub/logs. Настроечный секрет Site, если нужен для конфиденциального OAuth клиента, хранится только в runtime secret store. [Секреты Sites](https://help.openai.com/en/articles/20001339-creating-and-using-chatgpt-sites)
3. **Модель делегирована, разговор отдельно.** Сервер проверяет полномочие tool, точный payload, версию и ресурс. Он не получает проверяемого доказательства того, что пользователь сказал «да» в данном чате. В v1 проверка explain → confirm → dispatch лежит на инструкциях Project и интеграционной приёмке. Доверенный технический источник вызова — OAuth-соединение. Поля `confirmed`, утверждённый моделью actor, ключ из GitHub, история чата, текст комментария и иные подтверждения из payload отклоняются. Ошибка модели, которая вызвала разрешённый инструмент вопреки Project policy, остаётся риском этой модели делегации. Серверный тест сам по себе такой риск закрытым не объявляет.
4. **Два независимых допуска.** HTTPS-запрос без подходящего grant не создаёт зарегистрированное поручение. Корректно подписанная GitHub доставка без зарегистрированной ссылки и доверенного отправителя также не создаёт поручение. Webhook не принимает op, args, actor, permission или параметры цели из issue content. Ответы GitHub не интерпретируются как команды. Reader DTO размещает тексты постов, имена, цитаты, notes, evidence metadata и History в явно отделённых полях данных. Компонентов, которые исполняют HTML/Markdown, нет. Ссылки ограничены каноническими Vico ресурсами. Никакой arbitrary SQL, shell, fetch/proxy, рендер внешних URL, runtime discovery или общий model-callable executor.
5. **Нативное исполнение.** Actor передаётся из проверенного серверного контекста в существующую функцию. Новый transport gate не меняет действующий permission resolver, AP-10, ограничения ресурса, issuer floor, нативный CAS и History. Не формировать фиктивный `AuthSession` или запрос к браузерному route. Вынести общий admission/command из существующего action только там, где его нельзя вызвать напрямую. Браузер сохраняет текущие session/Origin/CSRF и рабочие форматы.

## 3. Проверка задачи до подтверждения и выполнение после него

1. **Проверка.** Защищённые read tools находят конкретные IDs и достают актуальные факты. Если нужно, отдельные inspection tools возвращают допустимость и ожидаемые поля для конкретной операции. Вход `prepare_task` принимает только ссылки на уже проверенные, индивидуально экспонированные операции и режим задачи. Он формирует неизменяемое описание, не создаёт исполняемого поручения и сам не может запустить эффекты. Описание содержит списки целей, последовательности и типизированные параметры, включая причины и обязательные объяснения, релевантные ревизии и последствия. Техническая запись описания имеет ограниченное хранение. Это снимок условий, не серверное подтверждение. Просмотр нескольких страниц допустим, подтверждение собирается для полного конкретного списка. Если данные недоступны или неоднозначность требует решения владельца, Мира не представляет непроверенную группу как готовую.
2. **Одна задача.** `taskId` выдаёт сервер. Хеш канонических данных включает режим, Owner grant, неизменяемые цели, их шаги, аргументы, ожидаемые версии и формат. Для одношаговой задачи те же правила применяются к одному элементу. Пользователь видит описанную задачу в чате. Мира помнит ссылку только в текущем разговоре, не восстанавливает право на запись из Project memory/другого чата и не подставляет после «да» новый `taskId`. Статус известной операции можно запросить отдельно, без права её выполнить.
3. **После подтверждения.** Соответствующий типизированный write tool работает по `taskId, targetIndex, stepIndex`. Параметры лежат в неизменяемом описании. Тип инструмента обязан точно совпасть с типом шага. Свободных полей для replacement target, args или новых шагов этот вызов не принимает. Все tools могут выполнить свой одношаговый вариант через тот же контракт. Для составных и массовых задач Мира вызывает нужные tools по порядку. Сервер проверяет доступность каждого шага под lock задачи. Нельзя перепрыгнуть через незавершённый зависимый шаг или повторно начать выполненный. Идущие подряд вызовы для разных целей обрабатываются последовательно, чтобы избежать гонок в общих ограничениях. Сервер фиксирует прогресс в транзакции. Набор утверждённой задачи не расширяется. Внутри инструмента используется та же цепочка доставки и одна каноническая запись.
4. **Составная задача.** Выполнять объявленные шаги по порядку. На `denied`, `stale`, `unavailable` или `outcome-unknown`, когда соответствующий результат установлен для шага, оставшиеся шаги ждут сверки либо помечаются `skipped`. `committed, changed=false` — завершённый допущенный шаг, если его каноническое постусловие выполнено. Уже применённые эффекты сохраняются. Новый дополнительный шаг требует новой задачи и разговорного подтверждения. После потери контекста Мира сначала читает итог. Прерванный прежний запуск не возобновляется по одному «да» из нового чата.
5. **Массовая задача.** Сервер принимает полный дедуплицированный список независимых целей. Объекты с зависимыми операциями или влиянием на один общий ресурс образуют одну упорядоченную последовательность. Среди независимых целей следующий объект может выполняться после локального отказа, stale или unknown предыдущего. У каждой составной цели собственное stop-on-first-failure. Общий недействительный grant или недоступность API/БД отражается как блокировка всех оставшихся целей, про которые это известно. Ни повторная выборка по фильтру, ни появление новой темы не меняют зафиксированный список. Каждый результат состоит из состояния цели и её шагов.
6. **Связанные версии.** Если шаг B зависит от собственного A, ожидаемая версия или ID результата A заранее формализуется ссылкой на конкретный committed receipt, например после Move. Сначала сравнить с точным постусловием A, затем проверить B в штатной транзакции. Сравнение может принять изменение, вызванное доказанным A, и обязано отклонить внешнее вмешательство. Новоизобретённая зависимость, динамический выбор другой цели или новое существенное последствие останавливают шаг перед эффектом.

## 4. Протокол и доставка

| Запись | Содержание |
| --- | --- |
| Запрос tool API | Версия протокола, фиксированный tool name, `requestId`, закрытые параметры reader/inspection. Для write — `taskId, targetIndex, stepIndex`. Actor и binding устанавливает сервер. |
| Запись Vico | UUID `requestId`, привязка/версия, закрытая фаза, схема аргументов, digest и срок технической доставки. У записи write хранится стабильный `commandId`, назначенный по `taskId/targetIndex/stepIndex`, а также ожидаемые условия из снимка. Повторная доставка не удлиняет сроки. |
| GitHub | Новый комментарий авторизованного GitHub App в одном inbox issue содержит только версию, тип `request` или `receipt`, случайный `ref` и техническую корреляцию. Ссылка не является bearer или параметром команды. Только конверт известного формата из проверенного источника сопоставляется уже существующей строке. |
| Tool result | `requestId, taskId, commandId` где применимо, `op, target, status, code`, `changed` при commit, разрешённые postcondition/version/event ID. Для read — проекция со временем, покрытием и курсором. Для задачи — упорядоченные состояния шагов по целям, skipped с причиной и отдельный статус транспортной выдачи. |

Запрос проверяется на неизвестные поля, дубликаты ключей, границы страниц, целочисленные версии и существующие доменные пределы текстов. PostgreSQL bigint передавать канонической десятичной строкой. Идентичный `requestId` с тем же digest возвращает ту же запись, с другим — `conflict`. Стабильность `commandId` при новом transport request ID для того же шага предотвращает второй эффект. ChatGPT не генерирует новый task для скрытого повторения.

Приватный GitHub App имеет только Issues для выделенного приватного репозитория. Worker проверяет HMAC `X-Hub-Signature-256` по исходным байтам до разбора webhook, тип `issue_comment.created`, числовые идентификаторы репозитория, app/installation, inbox, автора, валидную `requestRef` и состояние её записи. Принимается только зарегистрированный request, допускается совпадение после гонки «создание комментария → webhook → ответ API», поскольку ref уже сохранён и отправитель проверен. Повторы и редактирование не подменяют параметры. Reply того же App исключён из request parser. Комментарий принят долговечно до `202` в пределах лимита GitHub. Долгий ответ строится отдельно. [Подпись webhook](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries) · [GitHub webhook best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks) · [Installation access tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation)

Резерв — один инертный по умолчанию GitHub Actions workflow с явной передачей проверенного message ID через `workflow_dispatch` самим сервисом. Запуск производится после доказательства, что запрос ещё не начал исполняться и основной webhook потерян, в пределах бюджета. Workflow читает тот же issue, аутентифицируется GitHub OIDC и передаёт ссылку в тот же Worker. Worker проверяет issuer/JWKS, audience, сроки, repo/owner IDs, разрешённый workflow/ref, события и оригинальный комментарий через GitHub API. GitHub App получает дополнительное право Actions:write только при включении этого пути, доверенный ref фиксирован. Раннеру хватает `id-token:write` и `issues:read`. Он не исполняет текст, не имеет базы, токенов форума или возможности сам создать команду. Резерв восстанавливает доставку при доступном общем API. Cloudflare, Hyperdrive, общая БД, GitHub и допуск аккаунта остаются общими зависимостями. [Workflow dispatch](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event) · [GitHub Actions OIDC](https://docs.github.com/en/actions/reference/security/oidc)

Worker публикует ссылку на результат только после фиксации фактического исхода. Запрос статуса проверяет действующий grant, получение/публикацию соответствующего receipt и доступ к его проекции. Повтор отправки комментария использует ту же ссылку. Если API принял комментарий и ответ потерялся, поиск по App author, issue, `ref` и `commandId` восстанавливает доставку. Два одинаковых комментария представляют одну команду. Status может запросить повторную выдачу уже известного результата. При остановке в середине команды он лишь сверяет состояние.

## 5. Связь с каноническими возможностями форума

Точки входа используют те же адаптеры, которые `workers/app.ts` собирает для обычных маршрутов, и те же раздельные `WEB_HYPERDRIVE` / `HYPERDRIVE`. Модель видит отдельные tools. Сервер держит внутренний закрытый реестр со схемой, версией, разрешённым видом цели, функцией preflight, минимальной проекцией и ссылкой на каноническую функцию. Новый entrypoint разрешает только зарегистрированные функции. Штатные пути пользователя и админки сохраняют поведение. Следующие таблицы задают полный минимальный набор возможностей.

Изменяющие tools используют версию/состояние того, что показано владельцу. Если штатная версия уже есть, передать её в неизменном виде. Если у команды есть lock, но слабая или отсутствующая precondition, добавить в неё сравнение под тем же lock. Для pin/solved/best answer проверять релевантное topic-state под нативной блокировкой, для notes/appeals — состояние Case и соответствующей pending-записи. Для authorization нужна ревизия под общим mutex с обновлением каноническими writers и веб-входами. Сравнение одного хеша состояния пропускает A→B→A. Там, где старый снимок не должен переживать такой цикл, использовать монотонную ревизию нужного tuple либо коллекции. Не добавлять глобальную синхронизацию, если область и защищающий её lock уже определены.

`removeHelpDuplicate` в текущем writer может принять pending appeal в той же транзакции. Если в объяснённой команде этого эффекта не было, появившаяся после preflight апелляция вызывает stale до удаления связи. Если он входил в объяснение, сравниваются конкретная appeal, relationship и вид исхода. У Help-команд, переводящих pending signals в `superseded`, учитывать соответствующее множество, когда оно даёт persisted terminal результат. Изменившийся набор требует нового объяснения, прежний writer и прежний History остаются общими. [Help History в main](https://github.com/iliya1947/vico-forum/blob/c49897181388b4a78f8e8248dc6508551df576c4/docs/ADMIN_PANEL.md#L582-L607)

За пределами реестра остаются отсутствующие remove/archive/merge/bulk capabilities, arbitrary shell/SQL/fetch, edit-any, реактивация и hard-delete, чужие secrets/session ops, передача Owner, пользовательские AI-функции, autonomous moderation, личные настройки и production infrastructure control. Фиксированный набор вызывает только перечисленные единичные операции. Для большого набора передавать preflight и итог страницами с одним manifest ID. До первого допуска Worker закрывает список, фиксирует точное число целей и вычисляет digest по всему набору. Незакрытый или изменяемый список не исполняется. Границы размера и время обработки применяются к странице и отдельной операции. До подтверждения все страницы входят в один показанный список. Владелец видит, какие элементы остановил общий бюджет.

## 6. Квитанции, остановка и сверка

Использовать существующую PostgreSQL. Новые данные канала ограничиваются связью делегации, временными описаниями задач, входами/ссылками доставки и квитанциями отдельных шагов. Это эксплуатационные записи. Канонические History, уведомления и event producers остаются исходными. DB migration обновляет schema/journal/snapshot и уместные локальные ACL/manifest проверки. Stage-6 ACL не применяется на этапе реализации.

1. Зарегистрированный request переходит в `accepted` после валидного GitHub event. Executor атомарно переводит `accepted` в `started` с номером попытки. Уникальный `commandId` связывает шаг с этой записью. Повторы до старта сходятся в одном допуске. Сверка состояния не запускает effect. При потере пробуждения можно вновь доставить только принятый и определённо ещё не начатый запрос. `started` с истёкшим временем никогда не передаётся другому исполнителю.
2. Канонический writer под своими locks повторно проверяет право, выбранную строку/номер попытки, причинную precondition, применимость и доменные эффекты. Нативный effect, History, минимальный результат и изменение прогресса задачи записываются в одной существующей `pg` или Drizzle транзакции. Подключить запись квитанции к её настоящему client/tx. Для Complaints, AP-10 и деактивации переиспользовать нативные operation IDs. Для остальных добавить узкую возможность записи результата выбранного шага. Удерживать locks в одном порядке на web и integration; не брать дополнительные доменные locks после History. Внешние GitHub вызовы вне транзакции.
3. Revocation и write-commit сериализуются. Гонка confirm/веб-изменения разрешается нативным CAS. Для сверки `started` использовать тот же lock и номер попытки. Если установлено, что транзакция больше не может примениться, сверка может закрыть её номер и подтвердить отсутствие эффекта. Если нельзя доказать, что первый исполнитель больше не может закоммитить, статус остаётся `outcome-unknown`. Похожая строка History, текущее состояние с желаемым значением и наступление timeout доказательствами commit не являются.
4. Привязка живёт по срокам сессии/grant. Исполняемая доставка expires через 5 минут с регистрации либо раньше вместе с grant. Неисполненный снимок хранится до 24 часов, с обязательной сверкой канонических preconditions на применении. Эти сроки определяют хранение и доставку, а правило разговора зависит от ясности последнего объяснения. Просроченная доставка не начинает эффекта. Модель при этом может продолжить разговор и заново сверить условия. Подробные read payloads и временные аргументы удаляются по истечении срока либо после выполнения, минимальные квитанции сохраняются 30 дней для сверки. До закрытия replay окна хранить tombstone UUID/digest без приватных аргументов. Внешние ссылки ограничить разрешённым Vico origin, обеспечить `private, no-store`. После истечения снимка пользователь получает понятный статус и снова читает состояние.
5. Публикация GitHub receipt отделена от эффекта. Любой результат выдаётся только действующему grant, которому принадлежит запись, после повторной проверки допуска к соответствующей проекции. После повторной привязки того же exact Owner допустима только сверка минимальной старой квитанции с сохранённой принадлежностью этому Owner и Project integration, без старого приватного снимка или возобновления исполнения. Повтор публикации или чтения результата не вызывает нативной записи. Технические логи содержат корреляцию, код сбоя и длительность.

| Статус | Значение и поведение |
| --- | --- |
| `read-ok` / `pending` | Полученная проекция либо доставка/выполнение продолжаются. ChatGPT может прочитать статус по тому же ID. |
| `committed` | Есть транзакционная квитанция или однозначный нативный receipt той же команды. Показать фактическое изменение и цель. Нативный no-op сообщается как `changed=false` с установленной причиной. |
| `not-committed/denied` | Установленный отказ без эффекта. Например, неизвестный target, reserved Help, нарушенная иерархия, невалидная сессия или операция вне реестра. Сообщить точную безопасную причину. |
| `conflict/stale` | Снимок, версия, manifest или UUID/digest расходятся. Перечитать допустимое состояние и заново сформулировать задачу при желании владельца. |
| `unavailable` | Зависимость или бюджет остановили работу до старта либо доказан rollback. Неизвестный обрыв после старта не показывать таким отказом. |
| `outcome-unknown` | Потеря COMMIT ACK, неопределённое состояние после отправки или другая ошибка, при которой commit не исключён. Только чтение квитанции/History и восстановление доставки уже известного результата. Следующий зависимый шаг блокируется. |
| `skipped` | Шаг не начат, потому что предыдущий существенный шаг цели завершился неуспешно или общий доступ закрыт. Для массовой задачи независимые цели рассматриваются отдельно. |

Составная задача может содержать `committed`, `outcome-unknown` и `skipped` одновременно. Общая оценка и текст строятся из фактов по шагам. При транспортной паузе Мира сообщает, что ещё неизвестно, и продолжает запросом статуса без повторного dispatch. Если уточнённый статус завершил прежнюю неопределённость, произошедший эффект отражается в отчёте. После существенного сбоя оставшиеся шаги старой последовательности не запускаются автоматически.

## 8. Проверки по продуктовому контракту

Repository/local-CI использует built Worker, PostgreSQL 17, настоящий Better Auth и локально воспроизводимые GitHub webhook/API/OIDC, MCP и OAuth endpoints. Проверять штатный HTTP путь и канонический DB effect. Chromium нужен для локального OAuth входа/согласия и проверки сохранённых web flows. Нужны применимые `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm db:check`, `pnpm db:test`, build и targeted connected acceptance на одном implementation head.

| Критерии scope | Доказательство |
| --- | --- |
| 1, 8 — чтение и закрытый реестр | Позитивный тест для каждого read tool. Покрыть Forum/Admin, структуру, скрытый контент и protected revisions, Attention/Security, Users/меры/private projections, все Complaints группы и настройки. Для Monitoring проверить System, Accounts & authentication, Security, Forum, Localization & translations, Notifications, Files & attachments, Administration, Moderation, Background processes, Data, Integrations, а также Overview, scoped History, Event log и честную частичную доступность. Неизвестный tool, SQL/shell/fetch и unsupported operations дают ноль эффектов. |
| 2, 7 — паритет | Для каждого write tool сравнить результат, нативную History и уведомления с вебом на равном исходном состоянии. Проверить реальные versions/CAS, Help outcome и stale после создания appeal, reserved targets, hidden Move, overlapping permissions, issuer floor, no-op. |
| 3, 4 — разговор и доступ | Локально проверить реальные OAuth и exact Owner/session/active-account guards, токен чужого audience, подмену GitHub автора/репозитория, старый ref, запись токеном read-only, revoke между этапами. При интеграционной проверке отдельный Project читает сразу, объясняет каждую запись и вызывает write tool только после отдельного ответа Owner. Опровержения и новые цели, пересланная цитата, форумный prompt injection, вставка «да» из другой беседы и отсутствие owner turn дают ноль write calls. Подмена форумного/GitHub текста без действительной делегации даёт ноль серверных эффектов. |
| 5, 6, 10 — надёжность | Одновременные Worker/Actions, duplicate send, изменённые UUID/digest, loss до старта, после ACK, на COMMIT и после commit до reply, отказ History, rollback. При unknown доказать, что запрос статуса не повторяет запись. Сверить правильный фактический итог, а не HTTP/job. |
| 9–11 — приватность, стоимость и Stage 6 | Тестовые маркеры чувствительного payload отсутствуют в GitHub, Actions и логах. Проверить минимальные проекции, запрет выдачи с чужим grant, hard-stop бюджет и деактивированную внешнюю конфигурацию. В Stage 6 подтвердить на аккаунте поддерживаемость подключения, $0 и отсутствие Work/Codex/обязательной второй карточки. |
| 12 — составная задача | «Перенести тему 123 → закрыть → закрепить». После одного подтверждения выполнить первую операцию, создать stale на второй, доказать skipped третьей и сохранение первой. Проверить успешный сценарий с собственным изменением expected state и параллельный конфликт с вебом. |
| 13 — массовая задача | Фиксированные A/B/C. Создать D после объяснения, смоделировать локальный отказ одного объекта и unknown другого либо внутренний сбой составного target. Проверить, что независимые цели продолжаются, D не появляется и итог перечисляет каждый target/step. |
| 14 — запросный режим | Канонический reader проходит тест с типизированным внутренним контекстом без ChatGPT. При отсутствии запроса сбора/анализа нет. Нет внешнего scheduler, подписки на данные форума или новых оповещений. |

## 9. $0 и Stage 6

Workers Free публикует 100 000 запросов в сутки на аккаунт, 10 мс CPU на запрос и 50 subrequests. Hyperdrive Free публикует 100 000 SQL statements в сутки. Эти общие квоты включают работу форума. Расчёт на локальной приёмке измеряет суммарную стоимость обычного tool, максимальной страницы, прохождения одной цели и массового запроса. У сервиса ограниченные страницы, параллелизм, admission budget, время выполнения и deadline короткого опроса. Нулевой доступный бюджет закрывает новые вызовы. GitHub Actions расходует общую included compute quota только при явном резерве в рамках запроса. При отсутствии hard-stop с нулевой перерасходной стоимостью этот путь выключен. Pending status и ограниченная доставка происходят по запросу, без постоянного poller. Sites используется в пределах существующего Plus, сборка/обновление отделены от эксплуатации. [Workers](https://developers.cloudflare.com/workers/platform/limits/) · [Hyperdrive](https://developers.cloudflare.com/hyperdrive/platform/pricing/) · [GitHub included usage](https://docs.github.com/en/billing/reference/product-usage-included) · [Neon plans](https://neon.com/docs/introduction/plans) · [Sites](https://help.openai.com/en/articles/20001339-creating-and-using-chatgpt-sites)

После отдельного разрешения владельца сначала проверить платформенную связку на синтетических данных в обычном Project его аккаунта. Использовать Site без UI, штатное OAuth подключение, отдельный read tool, изменяющие tools разных категорий риска и минимальные синтетические команды через приватный GitHub. Убедиться, что поддерживаемая настройка разрешений работает на каждом типе операции и не требует карточки помимо разговора. Проверить неизменное число подтверждений, отсутствие межчатового переноса и запуск защищённого tool только после объяснения и ответа владельца. Несовместимость любого обязательного свойства фиксируется конкретным доказательством и блокирует выпуск. Это проверка целевого UX при активации, прежний исследовательский Worker PoC повторять не требуется.

Production migrations/ACL, OAuth/GitHub App/webhook secrets, запуск Actions, реальный Owner binding, deploy Worker, проверка head/health и внешний доступ выполняются только в пределах отдельного разрешения Stage 6. До допуска write проверить read-only E2E, остаток бюджета, действующий revoke и выключатель. После допуска проверить обратимую одиночную операцию, составную и массовую на синтетических данных, квитанцию, History, отказ/сверку и отключение. Полное deployed acceptance относится к фактически разрешённой конфигурации, включая отсутствие обязательной второй UI-карточки.
